# SHTANISHKIN — склад и маркировка для Авито

Telegram Mini App для ИП, который продаёт уже маркированную одежду, прежде всего штаны, через Авито Доставку. Сотрудник принимает вещи сканером, собирает заказы и фиксирует передачу перевозчику в одном интерфейсе. Backend выполняет действия Авито, готовит документы Честного знака, передаёт задания локальному подписанту и проверяет результаты.

Текущее состояние описывает код репозитория. Наличие клиента API и успешные автоматические тесты не подтверждают права реального аккаунта или работу конкретного токена УКЭП на Windows.

## Выбранные решения

- Один ИП и собственный складской учёт в PostgreSQL. Авито владеет статусом заказа и доступными действиями; ЧЗ — юридическим состоянием кода. Эти состояния показываются отдельно.
- Простой путь сотрудника: скан → сборка → подготовка → передача. Закупочные формы и обязательный ввод себестоимости не добавляем. Цена продажи для документа берётся из заказа Авито; закупочная цена не подставляется вместо неё.
- Входящие УПД подписываются в **Saby**. Приложение связывает вещи с уже обработанным документом ЧЗ и проверяет его состав и стороны. Автоматического подписания входящих УПД или клиента Saby в проекте нет.
- Реализован прямой канал ЧЗ: **True API + УКЭП на Windows-компьютере владельца ИП**. Приватный ключ и PIN остаются на токене/компьютере. Установка — через Telegram `/signer`.
- Реальные клиенты используются без пользовательского переключателя провайдеров и без искусственного успеха. Обезличенные фикстуры применяются только в автоматических тестах.
- `AVITO_WRITES_ENABLED=false` и `CHZ_DOCUMENT_SUBMISSION_ENABLED=false` — исходные настройки запрета отправок. Выключенная запись не заменяет ответ провайдера успешным результатом. Включение — отдельное решение владельца после проверки доступа, подписи и договорной/кассовой схемы.
- Штатное размещение: backend и worker на VPS, Mini App на GitHub Pages; публикация через GitHub Actions после пуша в `main`.

Самовывоз, собственная курьерская доставка, производство/импорт и эмиссия новых КМ не входят в текущую модель продаж. Условия CNC/RDBS в API не расширяют эту модель автоматически. Полноценные финансы, аналитика, смены, публикация объявлений и синхронизация остатков Авито остаются дальнейшим развитием; наличие таблиц или документации провайдера не означает готового пользовательского сценария. МойСклад не используется.

## Рабочий процесс

В «Настройках» сначала подключите ЧЗ: укажите ИНН ИП либо используйте ИНН уже одобренного Windows-подписанта. Для авторизации не нужен настроенный склад. Включите Windows с токеном УКЭП, затем выберите и подтвердите адрес отгрузки «Основного склада» из ЧЗ. При отсутствии адреса добавьте МОД для легпрома в профиле ЧЗ и обновите список. ФИАС и адрес сохраняются автоматически; подтверждение кассовой схемы в форме не запрашивается. Саму договорную/кассовую схему по-прежнему проверяют отдельно перед активацией отправок.

Меню «Основной склад» в разделе «Склад» позволяет выбрать другой склад или добавить новый (OWNER/ADMIN). Выбор используется для приёмки, остатков и экземпляров; при сборке заказа склад выбирается отдельно в форме. Открытые отгрузки остаются привязаны к исходному складу. Подключение ЧЗ не включает юридические отправки.

1. **Приёмка:** отсканировать каждую вещь. Backend разбирает GTIN/serial, получает подходящую карточку Национального каталога и сохраняет экземпляр в `AVAILABLE`. Повторный скан не увеличивает остаток. Отсутствующая, неоднозначная или недоступная карточка не создаёт новый товар. Отдельного подтверждения приёмки нет.
2. **Юридические сведения:** в настройках связать партию с входящим документом ЧЗ, уже подписанным в Saby. Worker проверяет документ, наличие кодов, ИНН сторон, владельца и состояние КИ. Физическая приёмка сама этих фактов не подтверждает; юридическая проверка нужна перед резервом/упаковкой.
3. **Заказ:** открыть его в «Заказах». «Подтвердить заказ» отправляет действие в Авито. **«Собрать заказ»** сопоставляет объявление с точным вариантом склада и резервирует экземпляры. При повторных заказах сохранённое сопоставление используется снова. Открытие списка заказов не создаёт резерв.
4. **Упаковка:** отсканировать все вещи посылки. После последней система ставит в очередь передачу полного состава маркировок Авито. Принятие проверяется по результату каждой позиции.
5. **Подготовка:** непосредственно перед передачей нажать «Подготовить к передаче». Формируются точные байты документа дистанционной продажи; Windows-агент подписывает их, worker отправляет документ при разрешённой записи, проверяет обработку и конечное состояние каждого кода.
6. **Передача:** после готовности подтвердить «Передал перевозчику» с фактическим временем и основанием. Резерв и физическое наличие списываются согласованно, без повторного уменьшения доступного остатка. Факт передачи вне приложения можно зарегистрировать как исключение, даже если юридическая обработка не завершена.
7. **Возврат:** открыть исходную посылку, отсканировать вещь и указать состояние. Исправный возврат становится доступным после осмотра и необходимого восстановления в ЧЗ. Затем тот же экземпляр продаётся в новом цикле. Брак и повреждённый код остаются исключениями; они не запускают автоматическую перемаркировку.

Отмена заказа **в Авито** и отмена **складской отгрузки** — разные операции. После отмены в Авито проверьте наличие вещей и отмените отгрузку в «Упаковке»: резерв освобождается, а уже выполненный вывод требует юридической компенсации. После фактической передачи используется возврат.

Документы, подписи и квитанции доступны в посылке. Экспорт разрешён OWNER/ADMIN/ACCOUNTANT и содержит исходные байты, CMS, публичный сертификат, внешний ID и сохранённый результат ЧЗ. Подпись сама по себе не означает юридического завершения.

## Локальный запуск

Нужны Node.js **24+**, pnpm **11** (в проекте закреплён `11.19.0`) и Docker Compose. Команды выполняются из корня репозитория.

```bash
test -f .env || cp .env.example .env
pnpm install --frozen-lockfile
docker compose up -d --wait postgres redis
DATABASE_URL=postgresql://avito:avito@localhost:5432/avito pnpm db:migrate
pnpm dev
```

Корневой `docker-compose.yml` запускает только локальные PostgreSQL/Redis. `pnpm dev` запускает API, worker и Vite. При уже существующей `.env` проверьте, что её `DATABASE_URL`/`REDIS_URL` указывают на выбранные локальные сервисы: одноразовое значение в команде миграции не переписывает файл.

- Mini App: `http://localhost:5173`.
- API: `http://localhost:3000`.
- Проверки: `/health/live` — процесс; `/health/ready` — PostgreSQL/Redis.
- OpenAPI: `/api/v1/openapi.json`.

Прямое открытие браузера не авторизует сотрудника: защищённым запросам нужна подписанная Telegram-сессия. Для HTTP/UI-разработки без запущенного бота можно использовать `NODE_ENV=development TELEGRAM_MODE=disabled SIGNER_TELEGRAM_ENROLLMENT_ENABLED=false pnpm dev`; это отключает Telegram runtime и установку подписанта, но сохраняет проверку доступа к API.

### Telegram при локальной разработке

В существующей `.env` задайте токен бота, HTTPS `MINI_APP_URL` и локальные подключения к PostgreSQL/Redis. Для разработки используется `TELEGRAM_MODE=polling`; один бот обслуживается одним polling-процессом. Удаление существующего webhook и переключение действующего бота требуют осознанного изменения его настройки.

`pnpm dev:telegram` запускает API/worker и временный HTTPS-туннель к API, настраивает меню Telegram и печатает команду сборки/публикации frontend с адресом туннеля. Файлы `.env` не переписываются. Этот режим рассчитан на отдельную среду разработки; штатный релиз действующего приложения выполняется через CI/CD.

Команды бота: `/start`, `/app`, `/signer`, `/id`, `/help`. Владелец не назначается автоматически первому пользователю. Для первоначальной выдачи прав:

```bash
pnpm telegram:owner <числовой_Telegram_ID>
```

После этого переоткройте Mini App. Настройка webhook/меню при первом запуске или изменении адресов выполняется командой `pnpm telegram:setup`; её не нужно вызывать при каждом рестарте.

## Конфигурация `.env`

Список полей и исходных значений находится в [.env.example](.env.example), валидация — в `apps/backend/src/config/index.ts`. Существующие секреты сохраняются. Ключ шифрования при переносе или перезапуске не генерируется заново.

| Настройки                                                             | Назначение                                                                                                    |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`, `REDIS_URL`                                           | Общие для API и worker хранилища                                                                              |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_INIT_DATA_MAX_AGE_SECONDS`            | Проверка Mini App-сессии; токен также нужен уведомлениям worker                                               |
| `TELEGRAM_MODE`                                                       | `disabled`, локальный `polling` или production `webhook`; обновления принимает API                            |
| `MINI_APP_URL`                                                        | Полный HTTPS URL frontend, включая путь репозитория Pages                                                     |
| `MINI_APP_ORIGIN`                                                     | Только origin frontend для CORS                                                                               |
| `VITE_API_BASE_URL`                                                   | Публичный адрес API, встраивается в сборку frontend; секретов здесь нет                                       |
| `TELEGRAM_WEBHOOK_URL`, `TELEGRAM_WEBHOOK_SECRET`                     | HTTPS webhook и секрет проверки входящих обновлений                                                           |
| `PUBLIC_API_URL`                                                      | Стабильный HTTPS origin backend для установщика и подписанта; не адрес Pages                                  |
| `MARKING_ENCRYPTION_KEY`, `MARKING_ENCRYPTION_KEY_ID`                 | Ключ AES-256 в Base64 и его ID; нужны для зашифрованных кодов, документов, подписей и сессий                  |
| `CHZ_NATIONAL_CATALOG_API_KEY`                                        | Ключ НК для атрибутов по GTIN; не заменяет авторизацию True API                                               |
| `CHZ_NATIONAL_CATALOG_ENVIRONMENT`, `CHZ_NATIONAL_CATALOG_TIMEOUT_MS` | Адресная среда НК и таймаут; не общий режим приложения                                                        |
| `AVITO_API_CLIENT_ID`, `AVITO_API_CLIENT_SECRET`                      | Серверная OAuth-авторизация Авито                                                                             |
| `SIGNER_TELEGRAM_ENROLLMENT_ENABLED=true`                             | Подключение Windows через Telegram; требует HTTPS API, токена бота, шифрования и включённого Telegram runtime |
| `CHZ_SUBMISSION_MODE`                                                 | Для реализованной прямой отправки — `DIRECT_TRUE_API`; пустое значение допустимо до активации                 |
| `AVITO_WRITES_ENABLED`                                                | Разрешение настоящих действий продавца и передачи маркировок                                                  |
| `CHZ_DOCUMENT_SUBMISSION_ENABLED`                                     | Независимое разрешение подачи юридических документов                                                          |
| `TELEGRAM_SETUP_CHAT_ID`                                              | Необязательный ID личного чата для проверки его меню                                                          |

`LOCAL_SIGNER_TOKEN` и `LOCAL_SIGNER_CERTIFICATE_THUMBPRINT` нужны только для прежнего ручного подключения при выключенной установке через Telegram. В выбранном процессе устройство само генерирует секрет, а сертификат закрепляется после подтверждения OWNER. Общий старый токен при включённом Telegram-подключении не принимается.

API и worker должны использовать согласованную конфигурацию, ключ шифрования и ID. Не выключайте `TELEGRAM_MODE` только у worker при включённом Telegram-подключении: конфигурация проверяется и в worker, хотя webhook он не обслуживает. Все секреты остаются на backend; в `VITE_*`, Git, логи и сообщения они не передаются.

### Подключение УКЭП

На Windows владельца нужны токен нашего ИП, драйвер, КриптоПро CSP, CAdESCOM и сертификат в хранилище текущего пользователя. Бот `/signer` → ZIP → «Установить.cmd» → сравнение кода и подтверждение компьютера в Telegram. Настройки Mini App также выдают ссылку; это право OWNER.

Агент работает от вошедшего пользователя Windows и запускается Планировщиком. AUTH подписывается присоединённым CMS, документы — отсоединённым CMS. Сервер проверяет привязку сертификата, ИНН, hash и lease; криптографическая проверка ГОСТ/цепочки/отзыва выполняется управляемым Windows-агентом. Независимого ГОСТ-верификатора на сервере нет.

Подробности, обновление и диагностика — в [инструкции подписанта](apps/local-signer/README.md). Закрытый ключ, PIN и настройки криптопровайдера не вводятся в Mini App и не отправляются на сервер.

## API и обработка сбоев

Источник контрактов — `packages/contracts`; OpenAPI формируется из тех же Zod-схем. Все пользовательские маршруты используют `Authorization: tma <Telegram.WebApp.initData>`; backend проверяет подпись, срок и актуальные права пользователя. Сессия не заменяется клиентским actorId или отдельным самодельным JWT.

| Метод и путь                                                        | Назначение                                                                                           |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `POST /api/v1/auth/telegram/verify`                                 | Текущий пользователь и роли                                                                          |
| `GET /api/v1/inventory`, `GET /api/v1/inventory/variants/:id/units` | Остатки и экземпляры с маскированными кодами                                                         |
| `POST /api/v1/inventory/receipts/scan`                              | Физическая приёмка `{requestId, raw, scannerProfile}`                                                |
| `GET /api/v1/orders`, `GET /api/v1/orders/:id`                      | Актуальные заказы Авито, статусы, состав, сроки и доступные действия                                 |
| `GET /api/v1/orders/:id/actions`                                    | Разрешение записи и состояние операций заказа                                                        |
| `POST /api/v1/orders/:id/actions`                                   | Постановка действия продавца в очередь                                                               |
| `POST /api/v1/orders/:id/courier-options`                           | Чтение интервалов курьера; адрес передаётся в теле, не в URL журнала API                             |
| `POST /api/v1/orders/:id/actions/:operationId/reconcile`            | Сверка неизвестного результата без новой отправки                                                    |
| `GET /api/v1/orders/:id/actions/:operationId/label`                 | Скачивание сформированной PDF-этикетки                                                               |
| `GET /api/v1/marking/*`, `POST /api/v1/marking/commands/*`          | Упаковка, отгрузки, возвраты, документы, настройки и исключения                                      |
| `POST /api/v1/local-signer/*`                                       | Выдача установщика, регистрация, одобрение через бота и работа агента; точные маршруты см. в OpenAPI |

Действия заказа реализованы по сохранённому контракту Авито: подтверждение/отмена, отправка/получение, передача/исправление трека, отделение возврата и параметры CNC при разрешённом действии. Интервалы курьера повторно проверяются перед записью. Этикетка ПВЗ генерируется асинхронно по `marketplaceId`. Передача маркировок запускается из упаковки, без произвольного ручного списка кодов. Проверка кода покупателя в ПВЗ предназначена для службы доставки и не включена в интерфейс продавца.

Старый `POST /orders/:id/confirm` сохранён закрытым для совместимости. Для настоящего подтверждения используется `/actions`. `mode: read_only` в GET-ответах заказов описывает только чтение этих маршрутов; это не переключатель среды и не ограничение всех операций приложения.

Чтение доступно OWNER/ADMIN/WAREHOUSE/ACCOUNTANT/VIEWER; складские команды и действия продавца — OWNER/ADMIN/WAREHOUSE. Настройки, необратимые списания и исправления — OWNER/ADMIN. Экспорт — OWNER/ADMIN/ACCOUNTANT; подключение Windows — только OWNER.

Ключевые правила:

- Один новый жест — один UUID. При потере ответа повторяются исходные UUID и payload. Полный DataMatrix передаётся без `trim()` и потери GS; коды не сохраняются в localStorage или аналитике.
- Намерение внешней записи и локальные изменения фиксируются в PostgreSQL транзакционно. BullMQ передаёт только `operationId`; worker восстанавливает очередь после потери Redis.
- Действия, маркировки и вывод одного заказа исполняются через общую PostgreSQL advisory-блокировку. HTTP не удерживает складскую транзакцию во время обращения к провайдеру.
- Перед упаковкой, подготовкой, штатной передачей и подачей подписанного вывода проверяются свежие статус, состав и цена Авито. Для подготовки требуется `ready_to_ship`.
- Успешный HTTP-код не равен успеху операции: проверяются business success, позиции и юридический результат. После таймаута мутация не повторяется вслепую. Если достоверной сверки для действия нет, оно остаётся требующим внимания.
- `/health/ready` не доказывает наличие УКЭП, авторизации ЧЗ или прав Авито. Для этого есть состояние интеграций.

## Публикация и перезапуск VPS

Штатный выпуск: проверить изменения → запушить в `main` → дождаться [CI/CD](https://github.com/wireside/avito-automatization/actions/workflows/cicd.yml). Frontend публикуется после успешного backend-деплоя. Ручной `pnpm deploy` остался для отдельной веточной схемы Pages/туннеля; он не заменяет выбранный Actions-релиз.

Workflow проверяет код и тесты, собирает backend-образ `linux/amd64`, передаёт его по SSH, проверяет checksum/ревизию, сохраняет `pg_dump`, приостанавливает worker, применяет миграции, заменяет API и запускает worker. Размещение API и Pages обновляется последовательно, поэтому соседние версии должны быть совместимы.

### Однократная настройка CI/CD

- На VPS используется `/opt/avito-dev` с существующими `.env`, `compose.yaml`, при необходимости `compose.override.yaml`, Nginx/TLS и постоянными томами. Сервисы: `api`, `worker`, `migrate`, `postgres`, `redis`; backend-сервисы используют `avito-backend:dev`. Файлы окружения и Compose скрипт деплоя не заменяет.
- На сервере нужны Docker Compose, Python 3, `curl`, `gzip`, `sha256sum`, `flock`. Docker/Nginx должны запускаться после перезагрузки.
- В GitHub создаётся environment `vps-development`, доступ к деплою ограничивается `main`. Его секрет `VPS_SSH_KEY` — отдельный ключ CI, не интерактивный ключ владельца. Публичная часть добавляется к существующим ключам сервера. Поддерживаемый текущим сценарием root-доступ нельзя считать ограниченным только публикацией, даже при SSH-опции `restrict`.
- Публичный host key для `VPS_KNOWN_HOSTS` берётся из уже доверенной серверной сессии. Проверка `StrictHostKeyChecking=yes` остаётся включённой.
- В Actions variables задаются `VPS_HOST`, `VPS_KNOWN_HOSTS`, при необходимости `VPS_USER` (по умолчанию `root`) и `VPS_PORT` (`22`), `VPS_HEALTH_URL`, `VITE_API_BASE_URL`. `VPS_DEPLOY_ENABLED=true` включается после настройки.
- Pages → Source: **GitHub Actions**. Environment `github-pages` ограничивается `main`. Приложение использует встроенный GitHub token; секреты приложения не переносятся в frontend или Actions.

Публичные адреса, закреплённые текущим workflow: API `https://177-203-58-144.sslip.io`, Mini App `https://wireside.github.io/avito-automatization/`. При смене API обновите публичную переменную сборки, `PUBLIC_API_URL`, webhook и соединение установленного агента; CORS задаётся origin страницы, а не полным URL Pages.

### После перезагрузки

Выполняйте в существующей серверной папке, не заменяя окружение и тома:

```bash
cd /opt/avito-dev
docker compose ps
docker compose up -d postgres redis api worker
curl --fail https://177-203-58-144.sslip.io/health/ready
```

Если перезапуску предшествовало только выключение сервера, миграции или настройка webhook повторно не нужны. Для новой версии миграции выполняет CI. При диагностике проверьте состояние интеграций, режим webhook и доступ контейнеров к Telegram; просматривайте логи локально, не публикуя содержимое `.env` и персональные данные.

При восстановлении сервера использовался Compose `extra_hosts` для `api.telegram.org` через серверную переменную `TELEGRAM_API_IPV4`. Это настройка существующего VPS, а не поле `AppConfig` или универсальный IP Telegram. Её нельзя удалять вместе с серверным override при очередном деплое; при сетевой проблеме адрес проверяется заново с обычной проверкой TLS. HTTPS-проверку не отключать.

Резервные копии CI в `/opt/avito-dev/backups` находятся на том же сервере; они не заменяют внешнюю резервную копию БД и ключа шифрования. При неудаче скрипт пытается вернуть предыдущий код, но не откатывает схему БД. Ручной откат к `avito-backend:previous` допустим только при совместимой схеме. `docker compose down -v` не является способом перезапуска рабочего сервера.

## Проверки

```bash
pnpm verify                 # форматирование, lint, типы, unit/HTTP-тесты, сборка
pnpm exec playwright install chromium
pnpm test:e2e              # браузерные сценарии, после сборки frontend
pwsh -NoProfile -File apps/local-signer/tests/policy.tests.ps1
```

Проверки PostgreSQL запускаются только на **отдельных чистых базах**: примените миграции с явным `DATABASE_URL`, затем используйте `RUN_INVENTORY_TESTS=true` для `packages/database/src/inventory.test.ts` и `RUN_MARKING_TESTS=true` для тестов маркировки/подписанта/действий. `RUN_DATABASE_TESTS=true` включает базовые проверки очереди. Приёмка проверяет первоначальные глобальные количества и использует отдельную базу. Точная последовательность и список файлов приведены в `.github/workflows/cicd.yml`; не запускайте их на рабочем складе.

Последний полный прогон кода: **219 unit/HTTP-проверок, 33 проверки PostgreSQL, 52 браузерных сценария, 21 проверка политики PowerShell**. Проверены возврат и повторная продажа того же экземпляра, отмена после вывода, документ утраты, конкуренция операций и восстановление очереди. Эти результаты относятся к зафиксированному прогону, а не автоматически обновляемому счётчику. Политика и синтаксис PowerShell проверены вне Windows; CAdESCOM, драйвер, PIN и отзыв сертификата требуют проверки на компьютере владельца.

Перед включением юридических отправок остаются проверка УКЭП на Windows, реальных прав True API/Авито, перехода кодов на ИНН ИП и договорной/кассовой схемы Авито. Настройки разрешения отправок не включаются автоматически от установки агента или успешного скана.

## Код и документация

TypeScript-монорепозиторий: Fastify, Telegraf, Vue 3/Vite/Vuetify, TanStack Query, PostgreSQL/Drizzle, Redis/BullMQ, Zod, Pino, Vitest и Playwright. Бизнес-сценарии находятся в `packages/domain/src/{auth,users,inventory,orders,marking,operations}`. SQL/транзакции — в `packages/database`, внешние клиенты — в `apps/backend/src/infrastructure`, связывание зависимостей — в `bootstrap`. API и worker — разные процессы одного backend-пакета.

Миграции `0000`–`0013` применяются версионно. `0010` удаляет прежний runtime провайдера с сохранением зашифрованной истории, `0011` добавляет квитанции, `0012` — Telegram-подключение подписанта, `0013` — журнал действий Авито. Таблицы будущих функций не являются основанием добавлять пользователю обязательные формы. `stock_balances` — производное представление; история движений и успешных документов не переписывается.
