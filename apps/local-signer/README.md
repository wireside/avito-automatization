# Установка подписанта через Telegram

Обычному пользователю не нужны PowerShell-команды, API-ключи и ручной ввод отпечатка сертификата.

1. На Windows-компьютере владельца ИП открыть нашего бота и отправить **`/signer`**. Бот также предлагает установку владельцу при входе, если подписант ещё не подключён. Альтернатива: Mini App → Настройки → «Подключить Windows».
2. По ссылке скачать ZIP, распаковать всю папку и запустить **«Установить.cmd»**. Ссылка действует 30 минут и позволяет зарегистрировать один компьютер. Новая ссылка отменяет предыдущую ещё не использованную.
3. Установщик найдёт действующий сертификат ИП с приватным ключом. Если их несколько — предложит стандартное окно выбора. ИНН и отпечаток читаются из публичного сертификата, а не вводятся пользователем.
4. Сравнить шестизначный код в окне установщика с сообщением бота и нажать в Telegram **«Подключить этот компьютер»**. Это заменит прежний подключённый компьютер. Без подтверждения задания подписи недоступны. Если сообщение задерживается, отправить `/signer`: бот покажет ожидающие запросы.
5. Дождаться сообщения «Подписант установлен». Агент добавится в автозапуск через Планировщик заданий и начнёт работу. Его состояние видно в Mini App.

При открытии установки из Mini App используется Telegram.WebApp.openLink, чтобы страница загрузки открывалась во внешнем браузере. Обычная вкладка, созданная из Telegram Web через target="_blank", может унаследовать запрет скачиваний. Если клиент не поддерживает внешний переход, скопируйте полную ссылку и вставьте её вручную в новую вкладку Chrome на Windows; часть после `#` должна сохраниться. Билет по-прежнему передаётся только в POST-body, CSP/frame-ancestors не ослабляется.

Установщик просит Windows разблокировать только `.ps1` в распакованной папке и запускает их с RemoteSigned. Он не отключает системную политику выполнения. Если организация запрещает запуск, администратор Windows должен разрешить/подписать доверенный пакет. При предупреждении Windows о скачанном файле проверьте источник архива.

## Что должно быть на Windows

При ошибке проверки CAdESCOM установщик показывает этап (`CREATE_STORE`, `OPEN_CURRENT_USER_MY` или `CLOSE_STORE`), HRESULT, версию и разрядность PowerShell. Ошибка открытия или закрытия хранилища не означает, что плагин отсутствует. Проверка открывает хранилище только на чтение, не изменяет ключи/сертификаты/PIN и не регистрирует COM-компоненты. Текст исходного исключения не выводится, поскольку может содержать приватные данные.

При диагностике на Windows PowerShell 5.1 прямой вызов `$store.Open(...)` падал с `0x80004003` в `GetTypeAttrForTypeInfo` динамического COM-слоя PowerShell. Через `Type.GetTypeFromProgID(...).InvokeMember(...)` то же хранилище успешно открылось на чтение, вернуло один сертификат и закрылось. Поэтому проверка установки и все обращения агента к CAdESCOM используют общий `crypto-com.ps1`: методы, свойства и индексируемый `Item` вызываются через IDispatch без `$comObject.GetType()`. Коллекции не разворачиваются конвейером PowerShell. Этот обход не переустанавливает КриптоПро и не меняет хранилища, ключи, сертификаты или PIN. После исправления передачи CPSigner через DispatchWrapper пользователь подтвердил на реальном Windows-компьютере успешную авторизацию ЧЗ с УКЭП и получение зарегистрированного адреса склада. Подпись и обработка юридического документа этим не проверены.

Нужны токен именно нашего ИП, драйвер, действующая лицензия КриптоПро CSP, CAdESCOM (КриптоПро ЭЦП Browser plug-in) и установленный сертификат в `Личное — текущий пользователь`. Этот этап необходим и для обычного входа в ЧЗ; приложение не устанавливает лицензии и драйверы автоматически.

Владелец должен оставаться вошедшим в Windows, токен — подключённым, ноутбук — включённым. После перезагрузки нужно войти в ту же учётную запись. Первый запрос PIN и его повторение зависят от драйвера и токена. Агент не хранит PIN и не обходит его запрос.

Приватный ключ УКЭП не экспортируется. Индивидуальный секрет доступа генерируется на Windows и сохраняется через **DPAPI текущего пользователя** в `%LOCALAPPDATA%\AvitoWarehouseSigner`; папка имеет ACL владельца и SYSTEM. Backend хранит только SHA-256 секрета. ZIP содержит одноразовый билет, а не постоянный секрет. Повтор установщика после потери сети использует сохранённое зашифрованное состояние и не создаёт второй компьютер.

## Настройка backend

- `PUBLIC_API_URL` — публичный HTTPS origin именно backend. В текущей локальной `.env` взят из существующего `VITE_API_BASE_URL`. Для `dev:telegram` адрес автоматически передаётся процессам из текущего туннеля; постоянная установка требует постоянного адреса API.
- `SIGNER_TELEGRAM_ENROLLMENT_ENABLED=true` — включить выдачу установщиков. Нужны существующие `TELEGRAM_BOT_TOKEN`, `MARKING_ENCRYPTION_KEY`, работающий API/worker и включённый Telegram runtime.
- Применить миграцию **0012**. Не заменять существующий ключ шифрования.
- Включить в Telegram webhook/polling типы `message` и `callback_query`. Код настройки `pnpm telegram:setup` уже содержит оба типа и команду `/signer`. После развёртывания новой версии обновить настройки бота этой командой.
- Сертификат и его ИНН сохраняются после подтверждения в PostgreSQL. `LOCAL_SIGNER_TOKEN` и `LOCAL_SIGNER_CERTIFICATE_THUMBPRINT` для нового пути не нужны; оставлены только для ранее настроенных ручных установок при выключенном Telegram enrollment. При включённой установке через Telegram общий старый токен не принимается.

`CHZ_DOCUMENT_SUBMISSION_ENABLED=false` и `AVITO_WRITES_ENABLED=false` остаются выключенными. Установка и авторизация не отправляют документы вывода/возврата. Для последующего прямого канала нужно отдельно выбрать `CHZ_SUBMISSION_MODE=DIRECT_TRUE_API` и разрешить записи после проверки кассовой схемы и прав API.

## Протокол

- `POST /api/v1/local-signer/install-link`: владелец, текущая Telegram-сессия → ссылка с билетом в URL fragment.
- `GET /signer/install`: публичная страница загрузки без билета в серверном HTML/логах. ZIP запрашивается POST-запросом.
- `POST /api/v1/local-signer/install`: билет → ZIP со скриптами и `connection.json`.
- `POST /api/v1/local-signer/register`: билет, публичный сертификат, hash индивидуального секрета и код сравнения → PENDING. Повтор с теми же данными идемпотентен.
- Запрос подтверждения сохраняется в durable queue; worker отправляет сообщение владельцу. Решение принимается только от действующего OWNER и только по его собственному запросу.
- `POST /api/v1/local-signer/status`: индивидуальный Bearer → ожидание/подтверждение/отклонение.
- `claim`, `submit`, `heartbeat`: только одобренное устройство, закреплённые signerId/сертификат/ИНН. Секрет старого компьютера перестаёт работать после замены.

AUTH подписывается attached CMS, DOCUMENT — detached CMS по точным UTF-8 байтам. Агент через КриптоПро проверяет подпись, цепочку, отзыв, ИНН и SHA-256. Backend проверяет закреплённый сертификат, lease и hash; самостоятельного ГОСТ-верификатора на сервере нет. Доступ к исходящему агенту не требует открывать входящие порты Windows.

Для остановки: Планировщик заданий → AvitoWarehouseSigner → Завершить. `uninstall.ps1` удаляет задачу; локальную конфигурацию удаляют отдельно. Для переноса на другой ПК — новая установка через `/signer` с подтверждением владельца.

ZIP, API, права и процесс подтверждения проверяются автоматическими тестами с фикстурами. Совместимость конкретного Windows/КриптоПро/токена проверяется на компьютере владельца; без доступа к нему она не подтверждена.

## Состав пакета и обновление

ZIP содержит `Установить.cmd`, `install.ps1`, `agent.ps1`, общий `policy.ps1`, `crypto-check.ps1`, общий `crypto-com.ps1`, `uninstall.ps1`, инструкцию и `connection.json` с одноразовым билетом. Распакуйте всю папку: `policy.ps1` и `crypto-com.ps1` нужны и установщику, и агенту. Установщик проверяет действующий ГОСТ-2012 сертификат с приватным ключом и 12-значным ИНН ИП, защищает секрет DPAPI, копирует агент/политику/COM-модуль и регистрирует задачу. Пути с пробелами и кириллицей поддерживаются.

Для обновления скачайте актуальный пакет через `/signer`, запустите установку и подтвердите устройство. После замены прежний индивидуальный секрет перестаёт работать. Не копируйте новый `agent.ps1` без соответствующих `policy.ps1` и `crypto-com.ps1` и не передавайте `config.json` другому пользователю Windows.

## Фоновая работа Windows

Установщик создаёт задачу `AvitoWarehouseSigner` в Планировщике под текущим пользователем: она запускается сразу и при последующем входе этого пользователя в Windows (`AtLogOn`, `Interactive`). Для запуска используется `powershell.exe -NoProfile -WindowStyle Hidden …`: постоянное окно консоли скрыто, но при диагностическом ручном запуске окно остаётся видимым. Закрытие видимой консоли ранее завершало сам процесс агента; это не было отдельным интерфейсом управления службой.

Это фоновая задача пользователя, а не системная служба с запуском до входа в Windows. Текущая схема использует CurrentUser/My, DPAPI текущего пользователя и интерактивный сеанс для возможного запроса PIN КриптоПро. Перенос под SYSTEM не является эквивалентной настройкой. После перезагрузки владелец должен войти в ту же учётную запись; блокировка экрана не равна выходу, но ввод PIN при заблокированном экране требует разблокировки. Во сне, гибернации и при выключенном компьютере агент недоступен. Автоматический вход и отключение сна установщик не настраивает.

Изменение `policy.ps1` действует на будущие установки. Уже созданную задачу можно обновить без переустановки и смены привязки: изменить её действие на скрытый запуск и перезапустить задачу. Это не меняет `config.json`, сертификаты, ключи УКЭП или PIN. Не добавляйте `-WindowStyle Hidden` к ручному диагностическому запуску, если нужно видеть строки ошибок.

## Что проверяет агент

До подписи сверяются ИНН, срок задания, тип/алгоритм, допустимая причина документа и SHA-256 точных байтов. AUTH требует `CHZ_AUTH`/присоединённый CMS, документы — разрешённый тип/отсоединённый CMS. Агент проверяет CMS через КриптоПро, сертификат подписанта, цепочку/отзыв; для AUTH дополнительно сравнивает извлечённое содержимое с исходным hash. Повтор передачи готовой подписи сохраняет lease и результат, не создаёт новую подпись на каждый сетевой retry.

`ready`/heartbeat показывает доступность агента, а не завершение юридического документа. При неверной цепочке, истёкшем сертификате, отсутствии ключа или ошибке подписи агент сообщает безопасный код; содержание исключения, сертификата, задания и PIN в лог не выводится. Получение нового сертификата/другой токен требуют нового подтверждённого подключения.

Для вызова `SignCades` объект CPSigner явно передаётся через `DispatchWrapper` как `VT_DISPATCH`, с извлечением `PSObject.BaseObject` без обращения к COM `GetType()`. По документации [КриптоПро](https://docs.cryptopro.ru/cades/reference/cadescom/cadescom_interface/icpsigneddata2signcades) первый аргумент — VARIANT с объектом подписанта; [Microsoft](https://learn.microsoft.com/en-us/dotnet/framework/interop/default-marshalling-for-objects) предупреждает, что при возврате объекта из .NET исходный `VT_DISPATCH` может стать `VT_UNKNOWN`. Это исправление передачи параметра для наблюдавшегося `STAGE=SIGN HRESULT=0x80004002`; после замены файлов пользователь подтвердил успешную авторизацию AUTH на реальном Windows/CAdESCOM с УКЭП. Успешная авторизация не подтверждает весь цикл DOCUMENT и обработки юридического документа. Автоматического повторного вызова SignCades с другим способом маршалинга нет. Windows-тесты проверяют обёртку на управляемом IDispatch-объекте; на других ОС эта проверка пропускается.

При ручном запуске ошибка выводится как `SIGNER_UNAVAILABLE STAGE=SIGN HRESULT=0x… LINE=…`. Этап указывает на поиск сертификата, heartbeat/claim, политику, конкретную настройку COM, создание/проверку подписи или отправку результата. HRESULT берётся из самого внутреннего исключения до попытки сообщить backend об ошибке. Логи не содержат сообщения исключения, исходную строку скрипта, stack trace, данные сертификата, payload или credential. Во время сетевых повторов submit выводится отдельная безопасная диагностика каждой неудачной передачи. Новые поля доступны после обновления файлов агента; сам старый `SIGNER_UNAVAILABLE` не раскрывает причину.

Для диагностического обновления уже подключённого компьютера остановите задачу `AvitoWarehouseSigner` и ручной процесс агента, сохраните копии `agent.ps1`, `policy.ps1`, `crypto-com.ps1` и замените эти три файла согласованным комплектом в `%LOCALAPPDATA%\AvitoWarehouseSigner`. Не заменяйте `config.json` и не запускайте установщик: DPAPI-секрет и привязка устройства сохраняются. Запустите агент вручную под тем же пользователем с прежним `-ConfigPath`, дождитесь ошибки и передайте только строку диагностики. Затем остановите ручной процесс и запустите задачу. При таком обновлении ключи УКЭП, сертификаты и PIN не меняются. Диагностика не добавляет отдельную тестовую подпись: агент выполняет обычные разрешённые задания backend.

Автономная проверка политики без токена:

```powershell
pwsh -NoProfile -File apps/local-signer/tests/policy.tests.ps1
pwsh -NoProfile -File apps/local-signer/tests/crypto-check.tests.ps1
pwsh -NoProfile -File apps/local-signer/tests/crypto-com.tests.ps1
```

Проверены синтаксис PowerShell и 25 сценариев чистой политики, включая ИНН, сроки, hash и пути с пробелами/кириллицей. Запуск проверки на PowerShell 7 вне Windows не подтверждает Windows PowerShell 5.1, CAdESCOM, доступ к закрытому контейнеру, запрос PIN или онлайн-проверку отзыва. Перед включением отправок это проверяется на Windows владельца. Установщик запускается через стандартный `powershell.exe`, как указано в `Установить.cmd`.

В CI эти же тесты с управляемыми фикстурами запускаются также на Windows PowerShell 5.1. Они проверяют передачу методов/свойств и индексируемого `Item`, сохранение коллекций, точных payload, boolean/числовых параметров attached/detached и исходного HRESULT. Это не криптографический тест и не доступ к реальному токену.
