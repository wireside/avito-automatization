# Задание для фронтенда и Figma: склад → упаковка → ЧЗ → отправка → возврат

## Объём и ограничения

Backend реализует локальный складской процесс и изолированную симуляцию юридических интеграций. Реальных изменений Авито/ЧЗ нет. `MARKING_PIPELINE_MODE=disabled` — значение по умолчанию; `simulation` доступен только в непроизводственной среде с отдельной БД. Каждый ответ нового API содержит `simulated`; симуляцию обязательно показывать явно. Существующий `/api/v1/orders` читает реальные заказы Авито, а новые отгрузки относятся к каналу `AVITO_SIMULATION`. Их нельзя визуально смешивать.

Это задание основано на текущем исходном коде Mini App, а не на сверке конкретного Figma-файла: ссылка на файл в задаче не передана. Макет Figma этой задачей не изменялся.

Главное продуктовое условие: короткий складской сценарий. Не добавлять обязательные закупочные цены, ручное создание приёмки, бухгалтерские документы, согласование карточек и мастер из множества шагов. Обычная приёмка остаётся сканированием. Нет отдельной страницы для каждой фоновой операции.

## Что существует во фронтенде

- `WarehouseView.vue`: приёмка сканером, список остатков.
- `StockBrowser.vue`, `UnitList.vue`: варианты и экземпляры.
- `ScannerCard.vue`, `CameraScanner.vue`, `ScanFeedback.vue`: переиспользуемый ввод DataMatrix и обратная связь.
- `ReceiptJournal.vue`, `ReceiptCatalogDetails.vue`: журнал текущей скан-приёмки и сведения карточки НК.
- `OrdersView.vue`: чтение заказов Авито, статусы и детали. Рабочего управления упаковкой/отгрузкой нет.
- `useInventory`, `useIntake`, `useOrders`: текущие запросы и состояния.

Существующий скан приёмки не превращать в скан упаковки: упаковка назначает уже существующий экземпляр и не увеличивает склад.

## Минимальная навигация

1. **Склад** — оставить текущий экран, дополнить признаком юридической готовности в карточке экземпляра.
2. **Заказы / упаковка** — список отгрузок и одна рабочая карточка заказа с камерой/сканером.
3. **Возврат** — короткий сценарий внутри карточки заказа или bottom sheet.
4. **Проблемы** — список только нерешённых исключений.
5. **Настройки** — только владелец/администратор: реквизиты и интеграционная подготовка.

Документы ЧЗ доступны вкладкой/панелью внутри заказа и из проблем. Отдельный большой реестр документов не обязателен для складского MVP.

## Основной путь сотрудника

### Приход

Открыть существующий экран и отсканировать вещи. По карточке НК происходит текущая локальная приёмка в AVAILABLE. Скан не требует закупочной цены и не подписывает УПД.

Не показывать «Юридически принято» только из-за успешного скана. Маленькая отдельная строка состояния: «Проверяем документы», «Готов к продаже» либо «Нужна помощь». Проверку/импорт выполняет backend; сотрудник не создаёт для каждой пары документ вручную. Документы поставщика передаются один раз пачкой через API владельцем/интеграцией.

### Упаковка

Открыть заказ → отсканировать каждую пару → увидеть `N из M`.

После последнего скана backend сам создаёт задание передачи маркировок; UI опрашивает карточку до PACKED. Дополнительная кнопка «Отправить маркировки» не нужна.

В нижней части одна основная кнопка **«Подготовить к передаче»**. Нажатие вызывает `prepare`. Показывать прогресс «Оформляем ЧЗ», автоматически обновлять карточку. При READY заменить кнопку на **«Передал перевозчику»**.

После физической передачи сотрудник подтверждает её по посылке/этикетке. Повторно сканировать все вещи не нужно. Время подставляется текущее; редактирование прошлого времени — только в исключении «Уже передано вне приложения».

Подготовку ЧЗ не запускать сразу при обычной упаковке за несколько дней до отправки. Она начинается непосредственно перед передачей. Подготовка действительна 30 минут; при истечении показать проблему владельцу, не обходить проверку готовности.

### Возврат

Открыть исходный заказ → «Принять возврат» → скан вещи → выбрать «Всё в порядке» / «Есть проблема».

При исправном товаре backend сам делает юридический возврат и выпускает товар из карантина после подтверждения. Дополнительная кнопка «Вернуть код в оборот» не нужна.

При проблеме предложить понятные варианты: брак, повреждённая маркировка, не тот товар. Вещь остаётся недоступной для повторной продажи. Не предлагать автоматическое уничтожение.

Факт оплаты и первичный документ возврата должны приходить из данных заказа/интеграции. Пока такие источники не подключены, API принимает их явно; макет должен предусмотреть компактный блок уточнения только при отсутствии данных, а не обязательную большую форму для каждого возврата.

## Экран 1. Очередь упаковки

Новый компонент `PackingQueueView`, связанный с текущим разделом заказов.

Карточка/строка: номер заказа, код посылки, количество вещей, сумма продажи, локальный статус, отдельный бейдж «Тестовый процесс». Действие — открыть карточку.

Состояния: загрузка; пусто; данные загружены; ошибка с «Повторить»; устаревшие сохранённые данные; режим выключен. Не показывать тестовую очередь как реальные новые заказы Авито.

API: `GET /api/v1/marking/shipments?offset=0`. Страницы по 50. Ответ содержит массив в `data`; если длина 50, можно предложить следующую страницу, не показывая выдуманное общее количество. Серверных фильтров/поиска пока нет: локальный поиск явно ограничен загруженной страницей.

## Экран 2. Рабочая карточка отгрузки

Новый `ShipmentWorkspace` или панель в `OrdersView`.

Верх: номер заказа, parcel_code, время подготовки/передачи, основной статус. Данные API в этом срезе используют snake_case; не угадывать camelCase.

Состав: название, размер, цвет, masked_code, цена продажи, physical_state, legal_state, packed_at, avito_marking_status. Полный DataMatrix не отображать и не добавлять в копирование/аналитику.

Три независимые строки:

- **Упаковка:** сколько вещей отсканировано.
- **Авито:** ожидает / принято / ошибка.
- **ЧЗ:** ожидает / обрабатывается / подтверждено / требует внимания.

`PACKED` сам по себе не означает вывод ЧЗ. `READY` означает завершение необходимых проверок данного тестового процесса. `HANDED_OVER` — физическая передача, `DELIVERED` — доставка. Чек/выплата не выводятся из этих статусов.

Сканер переиспользует существующие компоненты. Камеру запрашивать только после действия пользователя. Предусмотреть аппаратный сканер, вставку и закрытие камеры. Скан не должен автоматически уходить в существующий endpoint прихода.

Состояния после скана: принят; повтор запроса; не тот экземпляр; неизвестная вещь; неверный формат; юридическая блокировка; ошибка сети с неизвестным результатом. Повтор сети сохраняет исходный requestId и raw.

API:

- `GET /api/v1/marking/shipments/:id`: `data` = заголовок отгрузки и `items`.
- `POST /api/v1/marking/commands/pack`: requestId, shipmentId, raw, scannerProfile.
- `POST /api/v1/marking/commands/prepare`: requestId, shipmentId.
- `POST /api/v1/marking/commands/handover`: requestId, shipmentId, occurredAt, evidenceReference, occurredOutsideApp=false.

`evidenceReference` — реальная ссылка/номер подтверждения передачи или идентификатор сохранённого события. Не заполнять случайным текстом ради прохождения формы. Если оператор подтверждает передачу вручную, использовать согласованный идентификатор этого события и показывать источник «Подтверждено сотрудником».

Периодическое обновление во время фоновых операций: 2–3 секунды, затем 10–15 секунд. После ухода со страницы останавливать активный polling. При долгом ожидании показывать «Можно закрыть экран — обработка продолжится», не перезапускать подачу документа.

## Экран 3. Возврат

`ReturnReceiveSheet`: скан, результат сопоставления с исходной продажей, состояние вещи, необязательное пояснение с разумной подсказкой. Исходную вещь/цикл продажи backend определяет по отгрузке и коду.

API `POST /api/v1/marking/commands/return`:

- requestId, shipmentId, raw, scannerProfile;
- kind: CUSTOMER или UNCLAIMED;
- condition: GOOD / DEFECTIVE / DAMAGED_CODE / WRONG_ITEM;
- occurredAt — фактическое получение, evidenceReference, note;
- paid — подтверждённый факт оплаты;
- primaryDocument {number, date, name} — для оплаченного возврата.

После принятия показывать «Возврат получен», затем «Восстанавливаем ЧЗ». Товар не считать доступным до финального результата. Не предлагать редактировать юридическое состояние вручную.

Для невосстановимой маркировки текущий API не поддерживает автоматическую эмиссию нового кода. Если скан невозможен, показать «Нужна помощь владельца»; не подставлять код соседней пары и не выдавать неработающую кнопку перемаркировки за готовую функцию.

Частичные возвраты выполняются по одному экземпляру, без возврата остальных вещей заказа.

## Экран 4. Проблемы

Новый `MarkingIssuesView`; на главной достаточно счётчика и ссылки.

API `GET /api/v1/marking/issues?offset=0`; `GET /api/v1/marking/overview` даёт packed, ready, issues, pending, calendar_days.

Карточка проблемы: короткое объяснение, объект/заказ, фактическое событие, дедлайн при наличии, действие. Скрывать UUID в технические детали. Не требовать от сотрудника понимать True API, Redis, криптоподпись и типы документов.

Примеры текстов:

| Код                      | Текст                                           | Действие                      |
| ------------------------ | ----------------------------------------------- | ----------------------------- |
| SUPPLY_NOT_CONFIRMED     | Нет подтверждения документов поставщика         | Передать владельцу            |
| OWNERSHIP_NOT_VERIFIED   | Не подтверждено право распоряжения товаром      | Передать владельцу            |
| CODE_NOT_IN_CIRCULATION  | Код не готов к продаже                          | Открыть детали                |
| LEGAL_CHECK_STALE        | Проверка устарела                               | Обновить проверку             |
| LEGAL_OPERATION_PENDING  | ЧЗ ещё обрабатывает предыдущую операцию         | Ждать/открыть документ        |
| DOCUMENT_REJECTED        | ЧЗ отклонил часть документа                     | Исправить источник данных     |
| DOCUMENT_STATE_MISMATCH  | Результат документа не совпал с состоянием кода | Сверить; не отправлять заново |
| JOB_FAILED               | Фоновая обработка остановилась                  | Повторить после проверки      |
| LEGAL_DEADLINE_EXCEEDED  | Нарушен срок передачи сведений                  | Срочно владельцу              |
| HANDOVER_OUTSIDE_APP     | Посылка передана до завершения оформления       | Срочно проверить ЧЗ           |
| PREPARED_NOT_HANDED_OVER | Подготовленная посылка долго не передана        | Проверить посылку             |
| DAMAGED_CODE             | Повреждена маркировка                           | Помощь владельца              |
| WRONG_ITEM               | Вернулась другая вещь                           | Разобраться с возвратом       |

Текущий API не имеет endpoint «Закрыть проблему вручную». Не рисовать рабочую кнопку с таким действием. Некоторые сигналы являются историческими и требуют разбирательства; успех следующего HTTP-запроса не удаляет нарушение срока.

## Панель документов

Новый `MarkingDocumentPanel`, открывается из заказа/проблемы. Реестр API: `GET /api/v1/marking/documents?offset=0`.

Поля: дата, действие, статус, внешний ID, items с maskedCode, unitId, status, errorCode, reason, dueAt. В текущем API список документов общий, фильтр по shipmentId сервером не реализован; связь можно получить по unitId состава. При расширении API предпочтителен серверный фильтр, не загружать бесконечный общий реестр для одного заказа.

Показывать результат каждой строки: успешные не должны выглядеть ошибочными из-за одной отклонённой. Показывать signing_status отдельно от результата ЧЗ: PENDING, LEASED, RECEIVED, VERIFIED. RECEIVED означает только получение байтов подписи, без криптографического подтверждения. Реальный локальный подписант пока не подключён; складской сотрудник не выбирает сертификат и не вводит PIN. Для OWNER/ADMIN/ACCOUNTANT есть скачивание пакета документа; симуляционный пакет обязательно помечать тестовым, не называть действительной подписью УКЭП.

Владелец может выполнить:

- `correctDocument` {requestId, documentId, reason}: новая версия только отклонённых строк; уже успешные коды не подаются повторно.
- `retry` {requestId, operationId, reason}: повтор фоновой операции после исчерпания попыток с тем же бизнес-документом. Это не способ исправления юридически отклонённого состава.

Неизвестный результат — сначала сверка. Кнопка «Повторить вывод» для любого статуса недопустима.

## Карточка экземпляра на складе

Дополнить `UnitList` раскрываемой карточкой `UnitLegalStatus`.

API `GET /api/v1/marking/units/:id`: physical/current_state, legal_state, ownership_verified, observed_at, received_legally, pending, simulated, blockers. Показывать маскированный код, исходную складскую идентичность, дату проверки и понятный итог. Для списка не делать автоматический N+1-запрос по всем строкам: загружать юридические детали при раскрытии экземпляра.

AVAILABLE — физическое состояние после локального прихода. Оно не означает юридическую готовность. Существующий счётчик склада нельзя переименовывать в «Юридически готово к продаже».

## Настройки и импорт: только владелец

Одна компактная страница `MarkingSettingsView`, без мастера для кладовщика:

- Режим: выключено / симуляция (readonly, задаётся backend-конфигурацией).
- ИНН ИП, склад, ФИАС и адрес, подтверждение кассовой/договорной схемы.
- Состояние календаря и импорта документов поставщика.

Команды:

- configure {requestId, sellerInn, warehouseId, fiasId, address, fiscalEvidenceReference}; ИП — без КПП.
- calendar {requestId, days:[{date:'YYYY-MM-DD',working:boolean}]}; календарь загружает администратор/интеграция одним пакетом, а не сотрудник для каждого заказа.
- supply {requestId, documentNumber, documentDate, supplierInn, evidenceReference, unitIds}; одна пачка кодов к документу поставщика. Закупочной цены нет.
- check {requestId, unitId}; новая проверка кода.

Не предлагать API-ключи в обычных формах: они остаются на backend. Импорт supply в этой версии является симуляцией подтверждения по mock-фактам, а не подписанием реального УПД.

## Списание: исключение, не основной путь продажи

`DispositionDialog` доступен OWNER/ADMIN из карточки экземпляра/проблемы.

Варианты: утрата / уничтожение. Требуются ссылка на акт и его реквизиты {number,date,name}, фактическая дата и явное подтверждение необратимого действия. API dispose: requestId, unitId, reason=LOSS|DESTRUCTION, occurredAt, evidenceReference, primaryDocument, confirmation='CONFIRM_IRREVERSIBLE'.

Для обычной продажи нет кнопки «Списать ЧЗ». Это происходит автоматически при подготовке отгрузки. Брак не равен уничтожению, повреждение кода не равно потере вещи. Возврат поставщику и эмиссия новых КМ в этот MVP не входят.

## Отмена

Кнопка в карточке до фактической передачи. API cancel {requestId, shipmentId, reason, physicalPresenceConfirmed:true}. Один короткий вопрос «Все вещи этой посылки у вас?» и причина; подтверждение нельзя подставлять без действия сотрудника.

Если вывода ещё не было, освобождается резерв. Если вывод подтверждён — вещи уходят в карантин, backend оформляет отмену исходного документа и выпускает их после подтверждения. При неизвестном/частично отклонённом документе сначала требуется сверка; UI показывает блокировку. После физической передачи нужен возврат, кнопка отмены недоступна.

## Технический контракт frontend

- Источник runtime-схем и DTO: `packages/contracts/src/marking.ts`; публичная схема `/api/v1/openapi.json`.
- Авторизация: текущий `Authorization: tma <initData>`. actorId не передавать в body.
- GET: `{mode,simulated,data}`; команды: `{ok:true,simulated:true,replayed,result}`.
- Бизнес-ошибка: `{ok:false,code,blockers,requestId}`. 400 — входные данные; 401/403 — доступ; 404 — объект; 409 — конфликт/блокировка; 503 — режим выключен.
- Каждый новый жест получает crypto.randomUUID(). Сетевой повтор сохраняет UUID и payload. Нельзя новый UUID на каждый автоматический retry.
- Сохранять raw как есть, включая ASCII GS. JSON.stringify выполняет экранирование. Не использовать trim, ручную замену GS и очистку криптохвоста.
- Backend сам делает повторы и сверку. UI не отправляет prepare заново по таймеру.
- TanStack Query; не зеркалировать серверные статусы в Pinia. Инвалидация после команд: отгрузка, очередь, склад и проблемы.
- Не логировать request body скана, initData, полные КМ. В аналитике только action/result и технический requestId.
- Права: WAREHOUSE — упаковка, отгрузка, возврат, check; OWNER/ADMIN — дополнительно конфигурация, импорт, списание, исправления и симуляционные факты; ACCOUNTANT/VIEWER — просмотр.

## Макет Figma: что нарисовать

Обязательные состояния мобильного экрана (основной размер 390 px, плюс desktop 1440 px):

1. Очередь: загрузка / пусто / несколько заказов / ошибка / симуляция.
2. Карточка: 0 из N → частичный скан → последний скан → Авито обрабатывается → PACKED.
3. Передача: оформление ЧЗ → READY → подтверждение передачи → HANDED_OVER.
4. Блокировки: неверная вещь, нет подтверждённых документов, ЧЗ отклонил один код, неизвестный результат, подготовка устарела.
5. Возврат: скан → исправный → юридическая обработка → доступен; альтернативно брак/повреждённый код → проблема.
6. Отмена до отправки: подтверждение наличия; компенсация после вывода; блокировка после отправки.
7. Панель документа: часть строк успешна, одна отклонена, новая исправленная версия.
8. Проблемы: пусто / карточки разных типов / дедлайн / технические детали свёрнуты.
9. Настройки владельца: всё готово / нет документов / нет календаря / режим выключен.
10. Диалог утраты/уничтожения: реквизиты акта и подтверждение.

Переиспользуемые компоненты: `IntegrationStateBadge`, `UnitLegalStatus`, `PackingProgress`, `ShipmentLine`, `ShipmentActionBar`, `AsyncOperationNotice`, `BlockingReasonNotice`, `ReturnConditionPicker`, `MarkingDocumentPanel`, `IssueCard`, `SimulationBanner`.

На mobile основные действия закреплять снизу, скан и фокус ввода не терять после обновления данных. На desktop — состав слева, прогресс и действия справа. Цвета и отступы брать из существующих Vuetify-токенов проекта. В обычном сценарии backend-термины не показывать.

## Приёмочные сценарии frontend

- Новый приход проходит без закупочной стоимости и ручного создания приёмки.
- Последний скан сам запускает фоновые маркировки; нет дополнительной кнопки для каждой пары.
- Пока ЧЗ pending, передать обычным путём нельзя; ожидание переживает перезагрузку страницы.
- Потеря ответа и повтор исходного запроса не создают второй документ/движение.
- После отправки склад не уменьшается второй раз при доставке.
- Исправный возврат доступен только после завершения юридического восстановления.
- Повторная продажа возвращённой пары работает с тем же экземпляром и новым циклом.
- Симуляционные данные всегда отличимы от реальных заказов и юридических фактов.

## Дополнение: итоговый документ и локальный подписант

`GET /api/v1/marking/documents/:id` отдаёт карточку документа, строки и состояние подписи. `GET /api/v1/marking/documents/:id/export` (OWNER/ADMIN/ACCOUNTANT) отдаёт JSON-вложение с точными байтами документа в payloadBase64, SHA-256, типом документа, зашифрованной ранее и теперь экспортированной тестовой подписью в signatureEnvelopeBase64, состоянием обработки и источником проверки. В симуляции legalCompleted=false всегда. Полные коды есть внутри экспортируемого payload, поэтому загрузка доступна только уполномоченным ролям по явному действию, не аналитике и не публичному предпросмотру.

Новые компоненты: `DocumentSigningStatus` внутри панели документов и `LocalSignerConnectionStatus` в настройках владельца. Не добавлять отдельный мастер подписи каждой посылки. При включённом локальном агенте подписание должно идти в фоне; при отсутствии агента показывать «Ожидаем подпись» и уведомление владельцу.

Протокол для будущего локального агента (это не API браузерного frontend):

- `POST /api/v1/local-signer/claim` с Bearer LOCAL_SIGNER_TOKEN; body {signerId,acceptSimulation:false}. Возвращает task или null.
- task содержит taskId, leaseId, documentId, documentType, sellerInn, точный payloadBase64, payloadHash, expiresAt, simulated и algorithm=GOST_CMS_DETACHED.
- Агент проверяет ИНН, разрешённый тип документа, hash, срок задания и источник; подписывает именно декодированные байты без JSON-пересериализации. Закрытый ключ и PIN остаются локально.
- `POST /api/v1/local-signer/submit`: taskId, leaseId, signerId, payloadHash, signatureBase64, certificateBase64.
- Ответ verified=false до криптографической проверки. Сервер не считает присланные поля сертификата доказательством и не отправляет документ ЧЗ на основании одного успешного HTTP-ответа.
- Реального криптопровайдера проверки/доверенной цепочки/отзыва сейчас нет. Domain-порт DetachedSignatureVerifier и проверка ИНН, точных байтов, действия сертификата и проверки отзыва подготовлены. Мок подписанта имеет источник SIMULATION и никогда не выдаётся за УКЭП.

Задание на визуал дополняется четырьмя состояниями: ожидание локального подписанта; агент получил задание; подпись получена, но не проверена; подтверждённая тестовая подпись и дальнейшая обработка документа. Для администратора отдельно ошибка несовпадения ИНН/hash/истёкшего задания. Не выводить технические поля leaseId/algorithm сотруднику склада.
