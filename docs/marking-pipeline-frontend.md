# Frontend: Авито → упаковка → ЧЗ → передача → возврат

Описание текущего Vue/Vuetify Mini App и его контрактов. Экраны реализованы в коде; соответствие внешнему макету Figma отдельно не подтверждается. Закупочных форм, обязательной себестоимости и мастера подписания каждой посылки нет.

## Навигация и интерфейс

Доступные разделы: **Заказы, Упаковка, Склад, Проблемы**, а для OWNER/ADMIN — **Настройки**. Самостоятельных рабочих разделов финансов, команды, аналитики и публикации объявлений сейчас нет.

Мобильная навигация использует одинаковый цвет/opacity подписей и иконок; активная страница выделяется фоном. `DesignIcon` отображает SVG через маску с корректно экранированным URL, включая встроенные Vite data URI. Верхние действия заказа находятся в общем flex-контейнере с переносом и промежутками. Проверяем ширины 320/390/430/1512 px, отсутствие горизонтального переполнения и реальное отображение иконок.

| Раздел         | Компоненты и поведение                                                                                                              |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Склад          | Скан-приёмка по НК, остатки, экземпляры, раскрываемый `UnitLegalStatus`; физическое наличие отдельно от юридической готовности      |
| Заказы         | `OrdersView`: живой список/карточка Авито, статусы, сроки, фото и состав; фильтры и поиск по текущей странице                       |
| Действия Авито | `AvitoOrderActions`: доступные кнопки, короткие формы необходимых данных, состояния очереди, сверка результата и PDF-этикетка       |
| Сборка         | `ImportAvitoOrderDialog`: «Собрать заказ» → проверка состава/цены и резерв; точный вариант выбирается при первом сопоставлении      |
| Упаковка       | `MarkingPipelineView`, `ShipmentWorkspace`: очередь по 50, состав посылки, сканирование, подготовка и передача                      |
| Подключения    | `IntegrationStatusBanner`: CHZ-сессия, heartbeat Windows, API-настройки и отдельные разрешения отправок                             |
| Документы      | `MarkingDocumentPanel`: подпись, результат ЧЗ, результаты строк, исправление отклонённых и экспорт по роли                          |
| Возврат/отмена | Диалоги внутри посылки: фактическое наличие, скан и состояние вещи; карантин до нужного юридического восстановления                 |
| Проблемы       | Исключения и переходы к объектам; неизвестный результат не обходится новым выводом                                                  |
| Настройки      | Реквизиты ИП/склада, ФИАС, основание кассовой схемы, рабочий календарь, партия УПД и состояние подписанта; OWNER подключает Windows |

## Основной сценарий

1. Сканировать приход: подходящая карточка НК завершает физическую приёмку в AVAILABLE. Это не подпись УПД и не доказательство перехода кодов.
2. Владелец связывает партию с уже подписанным в Saby и обработанным документом ЧЗ. Backend проверяет состав документа, стороны, владельца и состояние КИ.
3. Открыть заказ. **«Подтвердить заказ»** — действие Авито; **«Собрать заказ»** — отдельное складское сопоставление и резерв. При известном объявлении повторный выбор варианта не обязателен.
4. В «Упаковке» сканировать каждую вещь. После последнего скана worker передаёт полный состав маркировок Авито. Не добавлять свободную форму ввода чужих кодов или кнопку отправки на каждой вещи.
5. Перед фактической передачей нажать «Подготовить к передаче». Документ и подпись обрабатываются в фоне. При выключенном Windows показывается ожидание; экран можно закрыть.
6. После подтверждения ЧЗ доступно «Передал перевозчику». Пользователь подтверждает реальный факт и его основание. Исключение «Уже передано вне приложения» записывает реальность и создаёт задачи сверки, не изображает юридическую готовность.
7. При возврате открыть исходную посылку, отсканировать вещь и указать состояние. Исправная вещь доступна для нового цикла только после осмотра и необходимого восстановления ЧЗ.

Подготовка и обычная передача требуют свежего подтверждённого заказа `ready_to_ship` и неизменного состава/цены. Отмена в Авито не снимает складской резерв автоматически: отгрузка отменяется после проверки вещей, с компенсацией уже выполненного вывода. После передачи применяется возврат.

## Действия Авито из карточки

Кнопки `confirm/reject/perform/receive`, `setTrackNumber/fixTrackNumber`, `acceptReturnOrder`, `setCNCDetails` основаны на `availableActions`. CNC/RDBS отображаются только при разрешённом провайдером действии и не меняют выбранную модель продаж через Авито Доставку. Подготовлены короткие формы трека, отделения/получателя возврата и необходимых параметров действия.

Для активного заказа можно запросить интервалы курьера; список и исходные контакты/адрес приходят из API. Перед записью worker повторно проверяет выбранный интервал. Для ПВЗ есть асинхронная генерация этикетки по `marketplaceId`. Скачивание выполняется авторизованным запросом через backend; «ещё формируется» не считается ошибкой отправки нового заказа. Метод проверки кода в ПВЗ, предназначенный службе доставки, в продавцовский UI не добавляется.

- `GET /api/v1/orders/:id/actions` → `{writesEnabled, operations}`.
- `POST /api/v1/orders/:id/actions` → `{operationId, replayed}`; тело `{requestId, action, data}`.
- `POST /api/v1/orders/:id/courier-options` с `{address?}` → допустимые интервалы.
- `POST /api/v1/orders/:id/actions/:operationId/reconcile` → постановка сверки.
- `GET /api/v1/orders/:id/actions/:operationId/label` → PDF.

Старый `/orders/:id/confirm` закрыт; новый frontend использует `/actions`. Поле `mode: read_only` у GET-заказов обозначает только свойства чтения, а не режим всей системы.

Состояния операций: PENDING, RUNNING, RETRY_SCHEDULED, SUCCEEDED, MANUAL_ATTENTION, CANCELLED. Один UUID сохраняется при повторе потерянного HTTP-ответа. Пока действие выполняется или его неопределённый результат блокирует заказ, новые команды не отправляются. `reconcilable` показывает возможность «Проверить результат»: этот запрос читает факты провайдера и не сбрасывает барьер повторной записи. Исчезновение кнопки в Авито не является достаточным подтверждением успеха. Для действий без надёжного чтения результата требуется выяснение у провайдера.

Состояние действий обновляется каждые 5 секунд; завершение/ошибка инициирует обновление карточки. Сам заказ читается каждые 30 секунд. Backend повторно проверяет актуальность перед записью — клиентские данные не являются разрешением на действие.

## Складские API, права и данные

- Чтение: `GET /api/v1/marking/{shipments,documents,issues,settings,overview,integrations}`; карточки `shipments/:id`, `units/:id`, `documents/:id`; экспорт `documents/:id/export`.
- Команды: `POST /api/v1/marking/commands/{importOrder,pack,prepare,handover,deliver,cancel,return,check,configure,calendar,supply,dispose,correctDocument,retry}`. Источники DTO — `packages/contracts/src/{marking,marking-views,order-actions}.ts`; OpenAPI — `/api/v1/openapi.json`.
- Пользовательская авторизация: `Authorization: tma <initData>`. actorId берётся на сервере. Складское чтение возвращает `{data}`, команда — `{ok:true,replayed,result}`; ответы Авито-действий имеют отдельные схемы выше.
- Чтение: OWNER/ADMIN/WAREHOUSE/ACCOUNTANT/VIEWER. Складские команды/действия продавца: OWNER/ADMIN/WAREHOUSE. Настройки, утрата/уничтожение, retry/исправление документов: OWNER/ADMIN. Экспорт: OWNER/ADMIN/ACCOUNTANT. Установщик Windows: только OWNER.
- Серверными состояниями владеет TanStack Query. Ошибки формы остаются рядом с действием; фоновые исключения показываются в проблемах. Полные DataMatrix и initData не пишутся в localStorage, логи или аналитику.
- `AVITO_WRITES_ENABLED=false`/`CHZ_DOCUMENT_SUBMISSION_ENABLED=false` отключают соответствующие отправки и показываются как состояние настройки. Это не выбор провайдера; подставного успеха нет.

## Документы и подпись

PENDING/LEASED/VERIFIED/EXPIRED задания подписанта и состояние юридического документа показываются независимо. VERIFIED означает проверку закреплённым Windows-агентом; сервер не имеет собственного независимого ГОСТ-верификатора. Успешная подпись не означает, что ЧЗ принял документ.

Экспорт содержит `payloadBase64` точных байтов, SHA-256, тип, `signatureEnvelopeBase64` с CMS/публичным сертификатом, внешний ID, статус и сохранённую квитанцию с наблюдениями по кодам. `legalCompleted=true` выставляется при подтверждённых документе и подписи. В файле могут быть полные коды; публичный preview не используется.

OWNER получает установщик в настройках «Подключить Windows» или в боте `/signer`. Нужно открыть ссылку на Windows владельца, распаковать ZIP целиком, запустить «Установить.cmd», сравнить код и подтвердить компьютер в Telegram. Срок ссылки — 30 минут. Подробности — [инструкция подписанта](../apps/local-signer/README.md). В Mini App нет формы PIN, закрытого ключа, общего bearer-токена или ручного флажка «подпись проверена».

## Что отразить в макете Figma

Макет должен отражать существующие взаимодействия:

- Раздельные «Подтвердить заказ» и «Собрать заказ», сопоставление только при необходимости, доступные действия Авито и их короткие формы.
- Состояния очереди, выключенной отправки, неизвестного результата/сверки и ожидания PDF.
- Посылка: 0/N, частичный скан, неверная вещь, ожидание/принятие Авито, ожидание Windows/ЧЗ, готовность и передача.
- Документ: подтверждён целиком, отклонена строка, неизвестный результат, экспорт по роли.
- Возврат: исправный/брак/повреждённый код, карантин и выпуск после ЧЗ.
- Состояния подключений, настройки владельца и просмотр проблем; скрытые команды при недостаточных правах.

Переиспользуются Vuetify-токены, сканер и обратная связь. Отдельная кнопка юридического списания для обычной продажи, закупочные экраны и ручной мастер подписи не нужны. Перед эксплуатацией требуется проверка на Windows с токеном и реальных API-правах; тесты frontend используют фикстуры и не отправляют юридические документы.
