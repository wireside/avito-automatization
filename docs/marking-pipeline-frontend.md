# Frontend: Авито → упаковка → ЧЗ → передача → возврат

Интерфейс реализован в текущем Vue/Vuetify Mini App. Новых закупочных форм, себестоимости, мастера подписания каждой посылки и выбора криптопровайдера нет. Figma-файл этой задачей не изменялся.

## Что доступно

| Раздел         | Реализованные компоненты и поведение                                                                                                                                         |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Склад          | Существующая скан-приёмка по НК, остатки, раскрываемый `UnitLegalStatus`; юридическая готовность отделена от физического наличия                                             |
| Заказы         | Настоящие заказы Авито, детали, «Взять заказ в работу» для OWNER/ADMIN/WAREHOUSE                                                                                             |
| Сопоставление  | `ImportAvitoOrderDialog`: состав/цена проверяются backend в Авито; точный вариант выбирается один раз, связь объявления сохраняется; варианты склада подгружаются страницами |
| Упаковка       | `MarkingPipelineView`, `ShipmentWorkspace`: очередь по 50, состав, сканирование, независимые состояния склада/Авито/ЧЗ                                                       |
| Подключения    | `IntegrationStatusBanner`: реальная CHZ-сессия, heartbeat Windows, состояние настройки API и разрешений внешних записей                                                      |
| Документы      | `MarkingDocumentPanel`: подпись, отдельный результат ЧЗ, результаты строк, исправление отклонённых, авторизованное скачивание пакета                                         |
| Возврат/отмена | Короткие диалоги внутри посылки; подтверждение факта, состояние вещи; возврат не становится доступным до подтверждения восстановления ЧЗ                                     |
| Проблемы       | Нерешённые исключения и переходы к объектам; неизвестный результат нельзя обходить повторным выводом                                                                         |
| Настройки      | OWNER/ADMIN: ИНН/ФИАС/адрес, основание кассовой схемы, календарь, партия входящего УПД, статус подписанта                                                                    |

## Основной сценарий

1. Сканировать приход обычным способом. По карточке НК товар появляется физически на складе. Это не подпись УПД и не подтверждение перехода кодов.
2. Владелец один раз связывает партию с уже подписанным в Saby и обработанным документом ЧЗ. Backend проверяет состав, ИНН сторон, обработку документа и актуальное владение кодами.
3. В «Заказах» открыть заказ и нажать «Взять заказ в работу». При первом объявлении выбрать точный вариант склада. При следующих заказах сохранённая связь используется автоматически.
4. В «Упаковке» сканировать каждую вещь. После последней backend передаёт весь состав маркировок Авито. Дополнительная кнопка на каждую вещь не нужна.
5. Непосредственно перед передачей нажать «Подготовить к передаче». Документ формируется и подписывается Windows-агентом в фоне. При отсутствии компьютера показать ожидание; экран можно закрыть.
6. После подтверждения ЧЗ появляется «Передал перевозчику». Коротко подтвердить фактическую передачу и её основание. Доставка не списывает склад второй раз.
7. Для возврата открыть исходную посылку, отсканировать вещь, выбрать состояние. Исправная вещь остаётся в карантине до восстановления кода; после подтверждения можно продать её в новом цикле.

Кассовая схема не определяется самим наличием заказа Авито. Подтверждение/отмена заказа на стороне маркетплейса остаётся в Авито; складская отмена в этом UI освобождает/восстанавливает локальный товар и юридическое состояние.

## API и состояния

- Чтение: `GET /api/v1/marking/{shipments,documents,issues,settings,overview,integrations}`; карточки `shipments/:id`, `units/:id`, `documents/:id`; экспорт `documents/:id/export`.
- Команды: `POST /api/v1/marking/commands/{importOrder,pack,prepare,handover,deliver,cancel,return,check,configure,calendar,supply,dispose,correctDocument,retry}`. Источник DTO/валидации — `packages/contracts/src/marking.ts` и `marking-views.ts`, OpenAPI — `/api/v1/openapi.json`.
- Авторизация текущая: `Authorization: tma <initData>`. actorId не приходит из браузера. Чтение возвращает `{data}`, команда — `{ok:true,replayed,result}`. Режима провайдера и искусственного признака успеха в ответе нет.
- Один жест — один UUID. При потере HTTP-ответа повторить исходные UUID и payload. UI не запускает документы по таймеру. Серверные состояния — TanStack Query.
- Raw DataMatrix передаётся без trim и ручной очистки GS. Не сохранять полный код/Telegram initData в localStorage, логи и аналитику.
- Состояния подписи: PENDING, LEASED, VERIFIED, EXPIRED; CHZ: подготовка/ожидание подписи/обработка/подтверждение/требует внимания. Проверка подписи закреплённым Windows-агентом не означает, что ЧЗ принял документ.
- `AVITO_WRITES_ENABLED=false`/`CHZ_DOCUMENT_SUBMISSION_ENABLED=false` показывают отсутствие разрешения отправки. Эти флаги не переключают провайдера и не создают успешные результаты.
- Ошибки пользователя остаются у поля/действия. Фоновые ошибки отображаются в проблемах. Нельзя предлагать «Повторить вывод» для любого статуса.

## Итоговые документы

Экспорт доступен OWNER/ADMIN/ACCOUNTANT по явному действию. Пакет содержит payloadBase64 с точными подписанными байтами, SHA-256, тип документа, signatureEnvelopeBase64 с CMS и публичным сертификатом, внешний ID, статус и сохранённую квитанцию с результатом/наблюдениями по кодам. `legalCompleted=true` только при подтверждённых документе и подписи. Полные коды внутри файла — не показывать его в публичном preview.

## Windows и настройка

В настройках OWNER есть кнопка «Подключить Windows»: выдаёт одноразовую ссылку, которую открывают на компьютере владельца. Тот же установщик выдаёт `/signer` в боте. После выбора сертификата нужно сравнить код и подтвердить компьютер в Telegram; вручную вводить токен и отпечаток не требуется. Подпись подключается один раз по [инструкции подписанта](../apps/local-signer/README.md). В обычном frontend нет формы PIN/ключа УКЭП, bearer token агента или ручного checkbox «Подпись проверена». Связь видна по heartbeat, авторизация ЧЗ — по действующей серверной сессии.

## Для обновления макета Figma

Нужно отразить уже реализованные состояния, а не проектировать дополнительные шаги:

- Карточка настоящего заказа и диалог первого сопоставления варианта; повторный заказ без обязательного выбора.
- Очередь/посылка на 390 и 1440 px: 0/N, частичный скан, неверная вещь, маркировки Авито ожидают/приняты, документ ждёт подпись/ЧЗ, готовность и передача.
- Компактное состояние подключений: всё подключено, Windows выключен, авторизация ожидается, записи не разрешены.
- Документ: подтверждён целиком, отклонена одна строка, неизвестный результат, скачивание по роли.
- Возврат: исправный/брак/повреждённый код/не та вещь; карантин и выпуск после ЧЗ.
- Настройки владельца и отдельный просмотр проблем; для VIEWER/ACCOUNTANT не показывать складские команды без права.

Переиспользуются действующие Vuetify-токены, сканер и обратная связь. На mobile основные складские действия закреплены снизу; на desktop состав слева, прогресс справа. Новые закупочные экраны и отдельная кнопка списания ЧЗ для обычной продажи не нужны.
