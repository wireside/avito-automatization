# СУЗ и перспективные возможности

Основной источник: [API СУЗ 3.0.40, руководство 5.03, редакция 67 от 24.09.2026](sources/suz-api-3.0.40.pdf). Это управление эмиссией, а не справочник любых поступивших джинсов. Для обычной поставки уже маркированных товаров сначала нужен Национальный каталог, документ поставщика и проверка КИ через True API.

## Разделение доступа

- `omsId` — идентификатор СУЗ; `omsConnection` — зарегистрированная установка интеграционного решения. Не взаимозаменяемы.
- `clientToken` передаётся заголовком СУЗ. Получение через True API требует УКЭП: запрос challenge, затем подпись и `/auth/simpleSignIn/{omsConnection}`.
- На одну установку доступен один действующий клиентский токен; новый аннулирует прежний. Для True API путь выдачи СУЗ-токена отличается от обычной сессии True API. Указанный срок — 10 часов: [с. 583-607](sources/suz-api-3.0.40.pdf#page=583).
- Ключ API Национального каталога не используется как `clientToken`, ключ регистрации или подпись.
- Для базового СУЗ v3 `X-Signature` — откреплённая CMS в Base64, когда подпись предусмотрена методом. Для GET подписывается PATH + QUERY, для POST — точные байты тела: [с. 13-16](sources/suz-api-3.0.40.pdf#page=13). Не переносить эти правила на регистрацию v2, которая допускает также присоединённую подпись.

## Контуры и различия версий

Руководство СУЗ [с. 31](sources/suz-api-3.0.40.pdf#page=31) указывает sandbox `https://suz.sandbox.crptech.ru`, production `https://suzgrid.crpt.ru`, ГОСТ sandbox `https://api.suz.sandbox.crptech.ru`. Production ГОСТ `https://api.suzgrid.crpt.ru` описан как пилот с планом промышленного использования со II квартала 2027 года. Это сведения конкретной версии PDF, не обещание текущей доступности.

В архиве есть **два разных контракта регистрации**:

| Контракт                                      | Источник                                                                   | Особенности                                                                                                                              |
| --------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/v2/integration/connection?omsId=…` | [Отдельная инструкция, с. 11-13](sources/dynamic-client-token.pdf#page=11) | Sandbox `https://suz-integrator.sandbox.crpt.tech`, production `https://suzgrid.crpt.ru:16443`; присоединённая либо откреплённая подпись |
| `POST /api/v3/integration/connection?omsId=…` | [Руководство СУЗ, с. 592-595](sources/suz-api-3.0.40.pdf#page=592)         | Откреплённая подпись; не заменять автоматически контрактом v2                                                                            |

Оба сохранены в Swagger отдельно; выбор подтверждать для аккаунта и среды. Готовые демонстрационные ключи из примеров не копировать в конфигурацию.

## Важные ограничения

- `GET /codes` выдаёт новые коды из буфера, поэтому HTTP GET **не означает отсутствие изменений**. Повтор после неизвестного результата может потребовать восстановление блока, а не вторую выдачу.
- `GET /order/list` описан для восстановления после полной потери данных; штатный постоянный polling им запрещён ([с. 170](sources/suz-api-3.0.40.pdf#page=170)). Для обычного поиска существует `/orders/search`.
- Руководство указывает общий предел 100 запросов/с по источнику/`omsId`; частные ограничения метода имеют приоритет. Не переносить этот предел на НК или True API.
- Создание заказа: до 10 разных GTIN, до 2 млн кодов для одной позиции; при нескольких GTIN до 150 тыс. на позицию; ограничения активных заказов и очереди — [с. 32](sources/suz-api-3.0.40.pdf#page=32). Это не ограничения сканирования входящей поставки.
- `dropout` СУЗ — отчёт об отбраковке/выбытии в контексте эмиссии. Он не заменяет документ дистанционной продажи True API и не вызывается по обычному флагу складского брака.
- Обработка отчётов асинхронна. Получение `reportId` не означает, что КИ уже перешли в нужное юридическое состояние.
- Разделы 5-8 содержат справочники, статусы, примеры и форматы кодов; приложение А ([с. 608-761](sources/suz-api-3.0.40.pdf#page=608)) описывает Квитирование 2.0. Это не дополнительные неизвестные HTTP endpoints.

## DataMatrix и оригинал скана

Для легпрома [с. 495](sources/suz-api-3.0.40.pdf#page=495) описывает AI `01` (GTIN), `21` (serial), `91` и `92` (криптографические данные) и разделители GS. Фиксированные размеры этой конкретной структуры не переносятся на все товарные группы.

Различать символ FNC1 в символике DataMatrix и строковое представление декодера. Не вставлять байт 232 в декодированную строку по одному рисунку. Оригинал скана не обрезать, GS сохранять; техническая нормализация идентификатора не изменяет сохранённые байты кода.

## Что пригодится позднее

1. **Повреждённый код и перемаркировка:** отдельный процесс с причиной, старым и новым КИ, документом True API и сохранением единственной физической пары. Наличие СУЗ не разрешает произвольную эмиссию для чужого товара.
2. **Собственное производство/импорт:** собственные карточки НК, модерация, подпись, эмиссия, нанесение, ввод в оборот, квитанции. Только после отдельного расширения бизнес-сценария.
3. **Агрегаты:** упаковки, КИТУ и раскрытие вложений при приёмке; группирование складских вариантов по размеру не является агрегацией КМ.
4. **Восстановление:** сохранённые ID заказов, блоков, отчётов и документов, реальная сверка после сбоя; не повторять эмиссию вслепую.

СУЗ также описывает авторизацию **МДЛП** ([с. 596-602](sources/suz-api-3.0.40.pdf#page=596)): два метода вынесены в [mdlp-auth.openapi.json](../openapi/chz/mdlp-auth.openapi.json) ради полноты архива. Они относятся к лекарствам и **не применяются к джинсам**. Общая вводная инструкция, примеры Postman, CryptoPro и старые требования к ОС сохранены как контекст провайдера, а не требования к стеку нашего приложения.
