# Каталог и автоматическая приёмка

## Реализованная часть: обогащение скан-приёмки

Backend читает прямой `GET /v3/product` по GTIN конкретного скана при новом GTIN или отсутствии сохранённого источника НК. Имя, артикул, размер/система, цвет, состав и происхождение сохраняются атомарно с приёмкой; mini-app сразу показывает сохранённые поля. Повторные приёмки используют локальные данные, а дубль/replay может обогатить старую пустую заглушку без увеличения остатка. Ручные карточки не перезаписываются; модели по одному артикулу не объединяются.

Ключ задаётся один раз как `CHZ_NATIONAL_CATALOG_API_KEY` в root `.env`, только для backend. После получения карточки товар полностью принят в AVAILABLE без проверки. Недоступность, отсутствие или неоднозначность карточки возвращают ошибку без нового экземпляра. Необязательные незаполненные атрибуты остаются пустыми и не блокируют найденный товар. Автоматическая цена, импорт документов, юридическая приёмка и массовый backfill не реализованы этим сценарием. Подробные настройки и поведение — в разделе Product attributes during scanned intake корневого README.

## Базовый сценарий: пустая база и первая поставка

Требование: сотрудник сканирует ЧЗ и видит осмысленное название, артикул, цвет, размер и закупочную цену без повторного заполнения карточек во всех следующих приёмках. МойСклад не используется как источник или обязательная зависимость.

Необходимы два потока данных:

1. **Описание товара по GTIN.** Национальный каталог или подтверждённый источник поставщика. Это относительно постоянные характеристики варианта.
2. **Условия покупки.** Конкретный документ поставки: поставщик, дата, строка, количество, цена, валюта, скидки и НДС. У разных поставок одного GTIN условия могут отличаться.

Без второго потока можно распознать товар, но нельзя достоверно вычислить закупочную стоимость конкретной пары. Прайс по согласованному договору может быть отдельным источником цены, если известны его период действия и применимость к поставке; произвольная последняя цена карточки не становится фактом покупки.

## Выбор метода НК

Источник: [API НК, с. 5-43](sources/national-catalog-api.pdf#page=5).

| Метод                   | Назначение                                                                                                     | Применение                                                                                    |
| ----------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `GET /v3/product`       | Опубликованные и архивные карточки; приватные атрибуты возвращаются только владельцу соответствующего аккаунта | Основной кандидат для распознавания GTIN поставщика                                           |
| `GET /v3/short-product` | Сокращённая карточка, атрибуты и их временные характеристики                                                   | Облегчённое чтение при подтверждённой достаточности ответа                                    |
| `GET /v3/feed-product`  | Полная своя карточка или предоставленный доступ через субаккаунт; не все статусы доступны                      | Администрирование собственных карточек, а не обязательный шаг при приёмке                     |
| `GET /v4/product-list`  | Список собственных карточек                                                                                    | Не является поиском всех товаров каталога и не нужен для холодного старта чужого ассортимента |
| `GET /v3/attributes`    | Атрибутивная модель для категории/ТН ВЭД                                                                       | Настройка сопоставления названия, модели, размера, цвета, состава и классификации             |
| `GET /v3/categories`    | Дерево категорий и связи с ТН ВЭД/группой                                                                      | Уточнение модели атрибутов; не угадывать категорию только по общему слову «штаны»             |
| `GET /v3/etagslist`     | Товары выбранного владельца и их хеши                                                                          | Будущая сверка изменений; не подменяет поиск по GTIN                                          |
| `POST /v3/mark-check`   | Принадлежность GTIN/ТН ВЭД маркируемым группам                                                                 | Классификация, не проверка существования и подлинности конкретного КИ                         |

Для `product`, `short-product`, `feed-product` есть одиночные `gtin` / `good_id` и строковые списки `gtins` / `good_ids`, разделённые `;`. Пакет — не более 25 позиций суммарно. Одиночный селектор и списковый одновременно использовать нельзя. При одновременных одиночных `good_id` и `gtin` приоритет у `good_id`; проекту проще отправлять только один вид селектора. Не преобразовывать GTIN в число.

У `product-list` максимум `limit=1000`, `limit+offset <= 10000`; более 10000 карточек за период даёт 413. Явно задавать интервалы и сохранять курсор. Формулировка периода по умолчанию в PDF необычна («за месяц вперед от текущей даты», с. 38), поэтому на неё не полагаться.

## Авторизация и ограничения

- Прямые серверы: sandbox `https://api.nk.sandbox.crptech.ru`, production `https://апи.национальный-каталог.рф`.
- Используется query-параметр `apikey` **либо** заголовок `Authorization: Bearer …`. True API прямо описывает ошибку 400 при совместной передаче; адаптер выбирает ровно один способ.
- Не путать прямой `GET /v3/product` с прокси True API `GET /api/v3/true-api/nk/product`. У прямого метода частный лимит 100 запросов в серии, у прокси — 10 запросов за 5 минут: [НК, с. 19](sources/national-catalog-api.pdf#page=19), [True API, с. 655](sources/true-api.pdf#page=655).
- Лимиты НК персональны для организации. Читать `API-Usage-Limit`, `API-Method-Usage-Limit`, при 429 соблюдать `Retry-After`. Новая серия начинается через пять минут от первого запроса. Примеры `1/500` и `1/10` не являются универсальными квотами.
- Для `product`, `short-product`, `categories`, `brands` использовать `ETag` / `If-None-Match`; 304 означает повторное использование сохранённой карточки, а не пустой товар. По PDF 304 не расходует лимит НК.
- Ключ хранится только на backend, не передаётся Mini App. Из логов HTTP-клиента, reverse proxy и ошибок удалять `apikey`, URL query и заголовки авторизации.

`CHZ_NATIONAL_CATALOG_API_KEY` уже читается backend; `CHZ_NATIONAL_CATALOG_ENVIRONMENT` выбирает `production`/`sandbox`, `CHZ_NATIONAL_CATALOG_TIMEOUT_MS` ограничен 500..10000 мс. Приложение не редактирует `.env`.

## Сопоставление атрибутов

Источник: [НК, с. 20-24 и 72-76](sources/national-catalog-api.pdf#page=20), [True API, с. 345-354 и 831-832](sources/true-api.pdf#page=831).

| Локальное поле      | Прямой НК                                                              | True API для `lp`                           | Правило                                                                           |
| ------------------- | ---------------------------------------------------------------------- | ------------------------------------------- | --------------------------------------------------------------------------------- |
| Название            | `good_name`, атрибут полного наименования                              | `name`, `fullName`                          | Хранить исходное название отдельно от отображаемого                               |
| Артикул/модель      | Подтверждённый атрибут в `good_attrs`, иногда идентификатор типа `sku` | `model`                                     | `sku` может быть локальным кодом, не обязательно артикулом производителя          |
| Размер              | Атрибут в `good_attrs`                                                 | `size`                                      | Сохранить метку и систему размеров; не приравнивать XS, 42 и 44 без подтверждения |
| Цвет                | Атрибут в `good_attrs`                                                 | `color`                                     | Сохранить исходное и отдельно нормализованное значение                            |
| Тип изделия         | Атрибут в `good_attrs`                                                 | `type`, `productKind`, `productKindOther`   | «Джинсы» не доказывает фасон «клёш» или «карго»                                   |
| Состав              | Атрибут в `good_attrs`                                                 | `structure`, `textileType`                  | Не переносить чужие сведения из соседней модели                                   |
| Производитель/бренд | Доступные атрибуты производителя, `brand_name`                         | `brand`, доступные сведения о производителе | Владелец GTIN/импортёр/поставщик могут быть разными лицами                        |
| Классификация       | Категории и атрибуты ТН ВЭД/ОКПД2                                      | `tnVedCode10`, `okpd2Code` при наличии      | Источник сохраняется; публикация требует проверки профиля классификации           |

Идентификаторы атрибутов брать из модели категории и реального ответа, а не из одного примера PDF. В `good_attrs` сохранять `attr_id`, `attr_name`, `attr_value`, `attr_value_type`, группу, уровень упаковки, GTIN и временные ограничения, если они доступны. Частный/отсутствующий атрибут не заполнять догадкой.

Первый кандидат модели: подтверждённый производитель/бренд + артикул + существенные различия модели. Точный вариант: размер/система/цвет + GTIN. Парa: валидированный GTIN + serial. Совпадение префикса GTIN, названия или фотографии не даёт основания автоматически объединять модели.

Если характеристики есть только в названии, допустимо правило конкретного поставщика с предпросмотром и первым подтверждением. Правило и источник сохраняются; неоднозначные значения не подставляются; найденная карточка не получает статус ручной проверки. Пользовательская подпись группы, например «Джинсы мужские 209-3», не заменяет идентичность варианта.

## Процесс будущего адаптера

1. При получении документа создать/обновить его локальную ревизию, строки и связь с поставщиком. Повтор импорта того же документа не создаёт второй приход. Исправленный УПД/УКД обрабатывается как новая ревизия с явной корректировкой стоимости.
2. При скане сохранить исходный DataMatrix без потерь, разобрать идентичность пары, проверить дубль. Криптохвост не отправляется в НК: для карточки достаточно GTIN.
3. Разрешить известный GTIN локально. Для неизвестного создать запрос обогащения с дедупликацией по GTIN, ограничением очереди и кэшем. Пока подходящая карточка не получена, новый экземпляр не создаётся: оператор видит ошибку и повторяет отправку. После получения карточки приёмка завершена сразу, без ожидания проверки.
4. Проверить соответствие ответа запрошенному GTIN/уровню упаковки. Несколько карточек для одного кода или конфликт источников требуют выбора, а не использования первого элемента.
5. Записать атрибуты и происхождение в `catalog_attribute_sources`, связать/создать `products`, `product_variants`, `variant_identifiers`. Уже созданный вариант обогащается без повторной приёмки пары и без переписывания движений.
6. По уникальному КИ найти соответствующую строку именно этого документа поставки. При нескольких строках одного GTIN с разными ценами одного GTIN недостаточно для выбора стоимости.
7. Создать цену слоя стоимости в `cost_layer_prices` с документом, валютой, НДС и способом расчёта; неизвестная цена не равна нулю. Хранить исходную десятичную строку и переводить в копейки без двоичной арифметики float.
8. Каталогизированная первичная приёмка уже завершена в AVAILABLE. Юридические наблюдения и документы сохраняются независимо и не создают дополнительный этап проверки в складском интерфейсе.

В этом полном алгоритме реализовано только обогащение физической скан-приёмки, описанное в начале страницы. Импорт поставки, стоимость, юридические проверки и автоматическое объединение моделей остаются отдельными сценариями.

## Где брать документ и закупочную цену

True API предоставляет `GET /api/v4/true-api/doc/list` и `/doc/{docId}/info`. Последний описывает в `body.products` поля `name`, `article`, `code`, `codeType`, `strNum` и отдельные сведения для ОСУ: [с. 416-427](sources/true-api.pdf#page=416). **В описанном наборе строк нет гарантированной закупочной цены за единицу.** Нельзя делить `sumNds` на количество всех кодов и объявлять результат ценой каждой пары.

Метод `/api/v3/true-api/doc/cises` прямо не предназначен для УПД/УКД. Для документов ЭДО нужен соответствующий интерфейс и исходный XML.

API «ЭДО Лайт» в архиве описывает списки, XML, архивы подписей и квитанции документов этого сервиса: [True API, с. 579-631](sources/true-api.pdf#page=579). Это **не универсальный API Saby** и не доказательство, что из него доступны все документы другого оператора. Для Saby отдельно проверить доступ, входящий УПД и его XML; переносить закрытый ключ в облако не требуется для проектирования импорта.

Минимальный контракт документа поставки: ID/ревизия/номер/дата; продавец и покупатель; строка; наименование/код поставщика; единица измерения; количество; цена, скидки, валюта, ставка и сумма НДС; связь строк с КИ или раскрытыми агрегатами. Если цена задана на упаковку или в иностранной валюте, преобразование в стоимость пары требует явного правила и источника курса.

## Проверка на реальном аккаунте перед реализацией

Получить обезличенные ответы НК по нескольким размерам одной модели и двум разным моделям. Проверить наличие `good_attrs`, состава, размера и артикула, отсутствие права на часть карточек, 404, пустой `result`, архивную карточку, 304, 429 и несколько результатов. Отдельно получить один реальный УПД из выбранного ЭДО. Наличие API Key не подтверждает все эти возможности; никаких юридических изменений для такой проверки не требуется.
