## Что означает полнота Swagger

Архив содержит **только PDF**, официальных JSON/YAML Swagger в нём нет. Восстановлены:

- 222 формальных объявления URL, включая повторения, направления входящих/исходящих документов и 30 видов заданий на одном `/dispenser/tasks`;
- 180 уникальных пар HTTP method + path в пяти действующих справочниках;
- ещё 18 исторических маршрутов/вариантов в отдельном deprecated-справочнике;
- описания, таблицы параметров и ответов из соответствующих разделов, ссылки на оригиналы и страницы;
- 20 разделов типов документов прямой подачи (4.1.2-4.1.21) внутри описания `/lk/documents/create`, а не выдуманные отдельные URL для каждого типа;
- 17 операций с дополнительными типизированными **подмножествами** схем, прежде всего каталог, авторизация и проверки приёмки.

Это **полный индекс формальных методов архива с исходной документацией**, но **не полная типизированная OpenAPI-модель всего протокола**. `source-documentation` оставляет схемы неизвестными; `typed-subset` описывает только явно выделенные поля. `additionalProperties: true` и `{}` не доказывают, что произвольный JSON принимается сервером. Условные поля юридических документов и все отраслевые модели не превращены в гарантированные DTO. Генерировать production-клиент или валидатор сразу на весь API по этим файлам нельзя.

У длинных разделов описание Swagger может быть сокращено; в таком случае это явно указано, а полный текст сохраняется в связанном PDF. Условия доступа, взаимозависимости параметров, XML/XSD и подпись всегда сверяются с оригиналом. Синтаксическая валидация OpenAPI не подтверждает корректность поведения сервера или полномочия аккаунта.

Покрытие не измеряется количеством уникальных слов или URL из примеров. Повторяющиеся маршруты объединены, а legacy-методы, повторные примеры и отраслевые варианты учтены отдельно: [coverage.json](../openapi/chz/coverage.json). Вводное руководство не имеет самостоятельного формального каталога URL; оно включено как описание последовательности действий, без дублирования методов из других руководств.

## Противоречия, которые нельзя замалчивать

1. **СУЗ v2/v3 регистрации:** разные адреса, версии и допустимая подпись. Оба контракта сохранены, без автоматического выбора.
2. **Прямой НК и прокси:** различаются лимиты и даже HTTP-метод `linked-accounts` (прямой GET, в True API POST). Не генерировать прокси подстановкой префикса.
3. **Цена DISTANCE:** таблица True API одновременно указывает обязательность и допуск отсутствия `product_cost`; нужна проверка применимости. Это не закупочная цена.
4. **Пагинация УД:** упомянуты 50 дочерних КМ по умолчанию и отдельный предел 36000. Полнота документа проверяется фактически, а не размером первой страницы.
5. **XML титула покупателя:** True API с. 600 указывает `application/x-www-form-urlencoded`, пример использует multipart. В Swagger для таких методов нет выдуманной однозначной модели загрузки.
6. **Пути legacy-подачи:** таблица отключений использует `/api/v3/lk/documents/create`, полное руководство задаёт `/lk/documents/create` относительно базы `/api/v3/true-api`. Различие отмечено; запрещён скрытый переход на другой маршрут.
7. **Срок жизни/JWT:** поддержка и сроки из редакции октября 2026 не превращаются в бессрочное обещание. Перед внедрением обновить документацию.
8. **НК product-list:** необычная формулировка периода по умолчанию не используется как надёжная спецификация; задавать период явно.
9. **ЭДО Лайт и Saby:** наличие API одного оператора не доказывает доступ к документам другого. Документов Saby, его API и реального УПД поставщика в архиве нет.

Ни API Key, ни удачный ответ отдельного чтения не подтверждают юридическую приёмку, закупочную цену, все поля каждой карточки, доступность всех методов или готовность склада к продаже. На этой задаче внешние аккаунты, рабочая БД и юридические документы не изменяются.
