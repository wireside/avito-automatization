# True API: юридическое состояние и документы

Источник: [True API v.747.0 от 21.10.2026](sources/true-api.pdf), 940 страниц. В этом документе перечислены применимые контракты и проектные ограничения. API-описание не заменяет действующие правила товарной группы, договорную модель Авито и доступ конкретного аккаунта.

## Авторизация, транспорт и токены

По [с. 3-10](sources/true-api.pdf#page=3):

- Серверы production `https://markirovka.crpt.ru`, sandbox `https://markirovka.sandbox.crptech.ru`. Версия входит в путь конкретного метода: `/api/v3/true-api/...` либо `/api/v4/true-api/...`; не заменять её глобально.
- `GET /api/v3/true-api/auth/key` → `uuid` и строка `data`. Локальный подписант формирует присоединённую УКЭП над исходной строкой; `POST /api/v3/true-api/auth/simpleSignIn` принимает `uuid`, подписанные данные в Base64 и условные поля `inn`, `details`, `unitedToken`.
- `unitedToken=true` запрашивает UUID-токен; ответ может содержать `uuidToken` и `expireDate`. Поддержка JWT в этой редакции указана до конца 2026 года. Не строить новую интеграцию на бессрочном использовании JWT; подтвердить актуальные правила UUID-токена перед запуском.
- Срок токена не более 10 часов, а для UUID дополнительно ограничен УКЭП/МЧД. Отзыв МЧД может аннулировать токен. Обновление токена не продлевает прежний автоматически.
- НК API Key не заменяет этот токен. True API «публичный» всё равно требует токен; «без токена» — отдельный тип приватности.
- Общий предел True API — 50 запросов/с на УОТ; это потолок, а не рекомендуемая нагрузка. Методические лимиты ниже имеют приоритет. Не переносить настройки НК или Авито в True API.
- В требованиях провайдера указан защищённый канал с сертифицированными СКЗИ/ГОСТ. Условия deployment/связности проверить отдельно: обычный успешный HTTPS-запрос не подтверждает выполнение всех требований эксплуатации.
- Успех может быть JSON, XML, ZIP или бинарным файлом, ошибка — другим типом содержимого. Учитывать `Content-Type`, статус и тело; для смешанных ответов допустим `Accept: */*`.

Национальный каталог, True API и `clientToken` СУЗ имеют разные жизненные циклы и способы передачи credentials. Не вводить один универсальный `CHZ_TOKEN` для всех трёх.

## Приёмка, проверка КИ и карточки

| Метод                                             | PDF страницы     | Что делать в проекте                                                                                                                                            |
| ------------------------------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/v4/true-api/product/info`              | 345-354, 831-832 | Карточки по массиву до 1000 GTIN; явные `size`, `color`, `model` для `lp` при наличии данных. Возвращаются только карточки с готовностью к маркировке и обороту |
| `POST /api/v3/true-api/cises/info`                | 298-312          | Подробное наблюдение КИ, GTIN, статус, производитель, владелец, особое состояние и ошибки по элементам                                                          |
| `POST /api/v3/true-api/cises/short/list`          | 312-320          | Проверка перед отгрузкой/приёмкой с сокращённым ответом; оболочка `result` отличается от `cisInfo` предыдущего метода                                           |
| `POST /api/v4/true-api/cises/search`              | 286-298          | Поиск КИ участника по фильтрам; максимум результата с пагинацией 10000, для больших объёмов нужны выгрузки                                                      |
| `POST /api/v3/true-api/cises/check`               | 335-336          | Верификация кода с криптографической частью, до 1000 значений, интервал не чаще 2 секунд. Это не POS-разрешительный режим                                       |
| `POST /api/v3/true-api/cises/history`             | 336-340          | История движения и расследование расхождений; ограничения приватности сохраняются                                                                               |
| `POST /api/v3/true-api/cises/aggregated/list`     | 340-341          | Раскрытие агрегатов; точный состав важен при документе поставки с КИТУ                                                                                          |
| `POST /api/v3/true-api/cises/history/list`        | 341-343          | История дезагрегации одного КИ                                                                                                                                  |
| `POST /api/v4/true-api/tn-ved/search`, `/rd/list` | 343-345, 358-363 | Справочники классификации и разрешительной документации                                                                                                         |

Для обычных запросов состояния передавать требуемый методом нормализованный **КИ**, а не автоматически весь DataMatrix с криптохвостом. Для `cises/check` нужна криптографическая часть. Адаптер формирует представление из валидированного парсинга, при этом оригинальный скан с GS хранится зашифрованным без изменений. Экранирование JSON выполняет сериализатор, а не ручная замена символов.

Массивы КИ ограничены 1000 там, где это явно указано контрактом. Ответы могут содержать успехи и ошибки одновременно при HTTP 200. Сохранять наблюдение и результат каждого КИ; пустой ответ/504 по одному коду не разрешает всю партию.

Провайдер использует `INTRODUCED` («В обороте»), `RETIRED` («Выбыл») и другие состояния. Локальное `IN_CIRCULATION` — бизнес-проекция, не строка для отправки провайдеру. `status`, `statusEx`, дополнительные признаки и время наблюдения сохраняются раздельно; неизвестное значение требует обработки, а не приведения к «в обороте».

Ни НК-карточка, ни одно состояние `INTRODUCED` сами по себе не подтверждают право приёмки и готовность к продаже. Сопоставить владельца/основание распоряжения, документ и фактический скан. Поставщик и производитель не подменяют друг друга.

Для `doc/{docId}/info` сам PDF одновременно упоминает стандартный вывод 50 дочерних КМ и отдельный предел 36000 для УД (с. 417). Параметры, тип документа и фактическую пагинацию проверять на реальном ответе; не полагаться на универсальное значение по умолчанию.

В структурированном теле УПД описаны названия, коды, номера строк и сумма документа; гарантированной цены каждой пары нет. Для точной стоимости сохранять исходный УПД/XML и правила НДС, валюты, скидок и единиц измерения. История документа ЧЗ не подменяет первичный источник закупочной цены.

Доступные API подписи/отправки титула покупателя, аннулирования и уточнения — внешние юридические изменения. Подключение чтения документов не разрешает их автоматическое выполнение.

## Вывод, возврат, отмена и перемаркировка

Общий маршрут подачи: `POST /api/v3/true-api/lk/documents/create?pg=lp`, [с. 44-48](sources/true-api.pdf#page=44). В оболочке обязательны `document_format`, `product_document` (Base64 точных байтов документа), `type`, `signature` (откреплённая УКЭП в Base64). Поля второго титула обязательны только для указанных типов и для остальных должны отсутствовать. Ответ HTTP 200 с ID документа не означает успешного завершения юридической операции.

| Сценарий                                      | Тип/поля из PDF                                                                                                              | Проектное применение                                                                                          |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Дистанционная продажа                         | `LK_RECEIPT`, JSON `MANUAL`, `action=DISTANCE`; `inn`, `action_date`, `products[].cis`; `product_cost` и применимые поля МОД | Подготовка вокруг фактической отгрузки, только при выбранном `DIRECT_TRUE_API`                                |
| Исправный возврат после дистанционной продажи | `LP_RETURN`, `return_type=REMOTE_SALE_RETURN`, `products_list[].ki`; условные `paid` и первичный документ                    | После фактического получения и осмотра, с проверкой причины исходного выбытия                                 |
| Отмена ошибочного вывода                      | `LK_RECEIPT_CANCEL`                                                                                                          | Отдельный процесс аннулирования последнего подходящего документа; не универсальная замена возврату покупателя |
| Повреждённая/утраченная маркировка            | `LK_REMARK` и подходящая причина, см. с. 220-228 и 789                                                                       | Новая маркировка с сохранением связи прежнего и нового КИ у одной пары                                        |
| Брак, утрата, уничтожение                     | Подходящий документ/причина по факту события                                                                                 | Не использовать СУЗ-отбраковку либо юридическое списание по одному локальному флагу брака                     |

Для `LK_RECEIPT` [с. 174-186](sources/true-api.pdf#page=174):

- `action_date` — реальная дата события, а не автоматически момент выполнения очереди.
- Для `lp` и `DISTANCE` указание МОД требуется по таблице на [с. 780](sources/true-api.pdf#page=780). `kpp` относится только к юридическим лицам; для ИП не выдумывать КПП. `fias_id` и МОД должны быть зарегистрированы и однозначно разрешаться.
- `products[].product_cost` описан как цена за единицу в копейках с НДС. Это цена выбытия, не закупочная стоимость. В таблице есть противоречие между «обязательный при DISTANCE» и допуском отсутствия значения (с. 182); перед production подтвердить поведение и применимость. Для проектного сценария предусмотреть корректную известную цену продажи, не подставлять закупочную.
- Требования к первичному документу зависят от причины; поля с формулировкой «строго не заполнен» нельзя добавлять универсальным DTO со всеми nullable-полями.
- Нет подтверждённого provider idempotency key в описании этого запроса. После timeout сначала искать/сверять результат; нельзя слепо пересоздавать юридический документ.

Для `LP_RETURN` [с. 123-128](sources/true-api.pdf#page=123): при дистанционном возврате `paid` обязателен на уровне документа или товара; сведения о первичном документе условно обязательны, в том числе при `paid=true`. Причины и приоритеты полей сверять со справочником [с. 791](sources/true-api.pdf#page=791). Описанный в таблице «владелец кодов» не отменяет необходимость проверить доступ конкретного участника.

Сохранять один канал ЧЗ на операцию и одну незавершённую операцию на КИ. Идемпотентность вывода — по паре и циклу продажи. Перед компенсацией сверять in-flight/неопределённые результаты. Физический возврат остаётся в карантине до осмотра и нужного юридического подтверждения.

## Выгрузки и перспективная аналитика

Источник: [с. 464-577](sources/true-api.pdf#page=464).

1. Создать задание `POST /api/v3/true-api/dispenser/tasks` с подходящими `taskType` и `taskSettings`.
2. Проверять `GET /dispenser/tasks/{taskId}` до `COMPLETED` либо терминального состояния.
3. Получить `GET /dispenser/results`, затем загрузить `/dispenser/results/{resultId}/file`. Учитывать несколько файлов, `available`, срок удаления и статус каждой части.
4. Импортировать CSV/XLSX версионированным парсером, с дедупликацией, provenance и курсорами. Само создание задания уже является внешней операцией, хотя не выводит товар из оборота.

Приоритетные типы: `FILTERED_CIS_REPORT`, `DOCUMENTS_ERRORS`, `VIOLATIONS`; в перспективе `CIS_ACS`, `ACS_DOCUMENTS`, отчёты по недействующим РД и исходящим документам. Идентификаторы остальных отчётов и ограничения по типу организации/группе брать из таблиц PDF, не считать все 30 отчётов автоматически доступными рознице.

Лимиты: poll задания — максимум 5/мин; получение result IDs и загрузка файла — максимум 12/мин для соответствующих методов. Срок хранения выгрузок отчётов — 10 дней; следить за `fileDeleteDate`, а не ожидать постоянного архива на стороне ЧЗ.

Средневзвешенная цена в аналитическом отчёте не является закупочной ценой нашего поступления. Юридический остаток ЧЗ не является физическим on-hand склада PostgreSQL. Расхождение создаёт задачу сверки, а не прямую замену баланса.

## Отдельные будущие возможности

Доступны методы согласий на раскрытие сведений (`agreement-registry`, с. 363-379), МОД/участников и договоров (с. 12-40), проверки разрешительных документов, истории агрегатов, предвалидации УПД и повторной обработки документов. Для каждого сначала подтвердить полномочия и сценарий. Розничная ККТ, алкоголь, табачная продукция, ОСУ и производство других групп не включаются в проект только потому, что их схемы есть в общем руководстве.
