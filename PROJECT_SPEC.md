# Автоматизация продаж маркированной одежды через Авито

## 1. Назначение проекта

Система автоматизирует обработку заказов маркированной одежды для ИП, который продаёт штаны только через Авито Доставку.

Основной рабочий интерфейс сотрудника склада — Telegram-бот со встроенным Mini App. Через него сотрудник должен открыть заказ, отсканировать DataMatrix, убедиться в соответствии товара заказу и запустить последующие операции в Авито, МоемСкладе и Честном знаке.

Обычный облачный МойСклад используется как складской и управленческий бэк-офис. На компьютере склада достаточно браузера и, при желании, USB-сканера DataMatrix. Локальное приложение «Касса МойСклад» и собственная ККТ в текущий контур не входят.

## 2. Зафиксированные бизнес-условия

- Продавец — ИП.
- Товар — маркированная одежда, прежде всего штаны.
- Товары обычно поступают уже промаркированными.
- Канал продаж — только Авито Доставка.
- Авито формирует и отправляет покупателю электронные чеки по используемой схеме расчёта.
- Физической розничной точки, самовывоза и собственной курьерской доставки нет.
- МойСклад используется через браузер, без кассового приложения.
- Ввод товара в оборот обычно выполняет производитель или импортёр. Для продавца важны приёмка, проверка состояния кода, вывод из оборота, возврат в оборот и брак.

Перед production необходимо получить пример реального чека Авито и проверить договорную схему: чей ИНН указан в чеке, присутствует ли маркировочная информация и изменяется ли после расчёта состояние конкретного кода в Честном знаке.

## 3. Границы ответственности систем

| Система | Источник истины |
|---|---|
| Авито | Заказ, состав заказа, доставка, допустимые переходы, принятые Авито коды маркировки |
| МойСклад | Номенклатура, модификации, склады, количество, резервы, отгрузки, возвраты, закупочная стоимость |
| Честный знак | Юридическое состояние конкретного кода маркировки |
| PostgreSQL | Связи между системами, поэкземплярные состояния, операции, идемпотентность и аудит |
| Redis/BullMQ | Временная доставка и исполнение фоновых заданий; не источник бизнес-истины |

Ни одна локальная запись не должна подменять подтверждённое состояние внешней системы. В интерфейсе отдельно показываются статусы Авито, МоегоСклада и Честного знака.

## 4. Ключевое решение по Честному знаку

Передача DataMatrix в Авито и вывод кода из оборота в Честном знаке — разные действия. Чек Авито также нельзя заранее считать доказательством выбытия конкретного CIS.

Система поддерживает взаимоисключающие режимы:

```text
CHZ_SUBMISSION_MODE=AVITO_OFD
CHZ_SUBMISSION_MODE=MOYSKLAD_MANUAL
CHZ_SUBMISSION_MODE=DIRECT_TRUE_API
```

- `AVITO_OFD`: контрольная продажа доказала, что код корректно выбывает через чек/ОФД в схеме Авито. Приложение только проверяет итоговый статус.
- `MOYSKLAD_MANUAL`: сотрудник формирует вывод или возврат через веб-интерфейс МоегоСклада, приложение отслеживает завершение.
- `DIRECT_TRUE_API`: документы создаёт наша система, подписывает локальный агент УКЭП и отправляет в True API.

Одновременно активен ровно один режим. Повторная отправка операции другим каналом запрещена.

## 5. Пользовательские сценарии

### 5.1. Получение товара

1. Номенклатура и модификации создаются или обновляются в МоемСкладе.
2. Для варианта товара фиксируются артикул, GTIN, размер, цвет и закупочная стоимость.
3. Приёмка поставки увеличивает количественный остаток.
4. При необходимости сотрудник выборочно проверяет DataMatrix и принадлежность кода ИП в Честном знаке.
5. Наша система синхронизирует изменившиеся товары и остатки.

Полный поэкземплярный реестр можно наполнять при приёмке либо при первом сканировании на заказ. Для быстрого запуска достаточно второго варианта.

### 5.2. Новый заказ Авито

1. Воркер получает заказ из Avito Order Management API.
2. По идентификатору объявления, артикулу или таблице сопоставления определяется модификация МоегоСклада.
3. В PostgreSQL создаются заказ и позиции.
4. В МоемСкладе создаётся один Заказ покупателя с `externalCode=avito:<orderId>`.
5. Количество резервируется.
6. Сотрудник получает уведомление в Telegram.

### 5.3. Комплектация и маркировка

1. Сотрудник открывает заказ в Mini App.
2. Приложение показывает товар, фото, размер, цвет и прогресс `N из M`.
3. DataMatrix считывается камерой телефона либо USB/Bluetooth-сканером как клавиатурный ввод.
4. Backend сохраняет исходные байты/строку без `trim`, сохраняя разделитель ASCII GS (`0x1D`).
5. Проверяются структура кода, GTIN, отсутствие дубликата, состояние экземпляра и соответствие позиции.
6. В транзакции экземпляр резервируется за заказом.
7. Фоновая задача передаёт код в Авито.
8. Успех показывается только после подтверждения или повторного чтения заказа из Авито.
9. После сканирования всех единиц заказ получает состояние `READY_TO_SHIP`.

### 5.4. Отгрузка

1. Проверяется, что все позиции промаркированы и Авито подтвердило коды.
2. В МоемСкладе создаётся ровно одна Отгрузка, связанная с Заказом покупателя.
3. Запускается выбранный режим работы с ЧЗ.
4. Система ожидает финальное подтверждение внешних систем.
5. Заказ помечается завершённым только после сверки.

### 5.5. Отмена до отгрузки

- снять резерв в МоемСкладе;
- отвязать код от заказа;
- вернуть экземпляр в `IN_STOCK`;
- не создавать возврат в оборот, если код не успел выбыть;
- сохранить историю действий.

### 5.6. Невыкупленная посылка

1. Получить фактическое состояние заказа Авито.
2. Проверить состояние CIS в ЧЗ.
3. Если код не выбыл, снять резерв/закрыть отгрузку и вернуть товар на склад.
4. Если код выбыл, сначала выполнить возврат в оборот, затем сделать товар доступным.
5. Не возвращать количество в доступный остаток до физического приёма посылки сотрудником.

### 5.7. Возврат покупателя

1. Сотрудник физически принимает и повторно сканирует DataMatrix.
2. Система проверяет, что код относится к исходному заказу.
3. В МоемСкладе создаётся Возврат покупателя.
4. Для товарного состояния `GOOD` запускается возврат кода в оборот.
5. После подтверждения ЧЗ экземпляр становится `IN_STOCK`.
6. Для состояния `DEFECTIVE` товар перемещается на склад «Брак» и не появляется в доступном остатке.

### 5.8. Брак, потеря или повреждение кода

- оформить складское списание либо перемещение на «Брак»;
- выбрать допустимую причину операции ЧЗ;
- потребовать подтверждение пользователя перед необратимым действием;
- сохранить внешний идентификатор документа и результат обработки;
- не использовать отмену ошибочного документа как замену реальному возврату товара.

## 7. Технологический стек

- Node.js LTS и TypeScript в strict-режиме.
- `pnpm` workspace, без микросервисного фреймворка.
- Fastify для HTTP API и Telegram webhook.
- Telegraf для Telegram-бота.
- React + Vite для Mini App.
- PostgreSQL как постоянное хранилище.
- Drizzle ORM с драйвером `node-postgres` для запросов, связей и транзакций.
- Drizzle Kit для code-first схемы и версионируемых SQL-миграций.
- Redis + BullMQ для фоновых заданий, retries и rate limiting.
- Zod для проверки конфигурации и входных DTO.
- ZXing `BrowserDatamatrixCodeReader` для камеры.
- Pino для структурированных логов.
- Sentry/OpenTelemetry для ошибок и трассировки.
- Vitest, Testcontainers и Playwright для тестирования.
- Docker Compose для локальной разработки и первого production-развёртывания.

## 8. Структура monorepo

```text
apps/
  backend/             Fastify, Telegraf и два entrypoint: API и worker
  mini-app/            React/Vite интерфейс
  local-signer/        только для DIRECT_TRUE_API
packages/
  domain/              состояния, правила и use cases
  database/            Drizzle schema, relations, migrations и db client
  contracts/           Zod-схемы и общие DTO
  integrations/        адаптеры Avito, МойСклад и ЧЗ
  queue/               имена заданий и общая политика retries
  observability/       логирование, метрики, trace context
docs/
  adr/                  архитектурные решения
  api-fixtures/         обезличенные ответы внешних API
```

Это один Git-репозиторий и модульный монолит. `backend` имеет два независимо запускаемых процесса: HTTP/Telegram API и BullMQ worker. Mini App собирается и развёртывается отдельно, но использует общие контракты из того же репозитория.

Telegram-бот не является отдельным сервисом: Telegraf подключается к Fastify как webhook-адаптер и вызывает те же application use cases, что и HTTP API. Бизнес-логика, доступ к БД и интеграции в обработчиках бота запрещены.

Отдельные Git-репозитории потребуются только при появлении независимых команд, разных циклов релизов или отдельной границы доступа. Для одного разработчика и ИИ-агента они замедлят синхронизацию DTO, миграций и версий.

### Правила Drizzle

- TypeScript schema в `packages/database` — источник схемы БД.
- Для обычных CRUD и связей использовать query/relational API Drizzle.
- Для `FOR UPDATE`, `SKIP LOCKED`, специальных PostgreSQL constraints и сложных отчётов использовать `sql` Drizzle либо проверяемый SQL внутри миграции.
- Генерировать миграции командой `drizzle-kit generate`, проверять сгенерированный SQL и коммитить его вместе со snapshot.
- Применять миграции отдельным deployment job через `drizzle-kit migrate`, а не одновременно при старте каждого API/worker процесса.
- `drizzle-kit push` допускается только для локального прототипа; production и общие окружения работают только через версионируемые миграции.
- Не добавлять второй ORM или дополнительный SQL builder.


Обязательные ограничения:

- уникальный `avito_order_id`;
- уникальный `cis_hash` для активного экземпляра;
- уникальная связь внешней сущности с локальной;
- уникальный `idempotency_key` операции;
- внешние идентификаторы МоегоСклада и Авито хранятся отдельно;
- деньги хранятся целым количеством копеек, не `float`.

Полный код маркировки не попадает в обычные логи, аналитику или ошибки. Хранить его зашифрованным только пока это необходимо для незавершённой операции; после завершения оставить безопасный идентификатор, GTIN, серийную часть в допустимом виде, hash и маскированное представление. Политику хранения уточнить по актуальным требованиям ЧЗ до production.

## 11. Идемпотентность и отказоустойчивость

Пример ключей:

```text
avito:set-marking:{orderId}:{orderItemId}:{cisHash}
moysklad:create-order:{avitoOrderId}
moysklad:create-demand:{avitoOrderId}
moysklad:return:{avitoOrderId}:{returnSequence}
chz:withdraw:{cisHash}:{reason}
chz:return:{cisHash}:{returnSequence}
```

Алгоритм операции:

1. Заблокировать доменную строку `FOR UPDATE`.
2. Проверить допустимость перехода.
3. Создать или получить существующую `integration_operation`.
4. Зафиксировать транзакцию.
5. Поставить `operationId` в BullMQ.
6. Выполнить внешний вызов с timeout.
7. Сохранить запрос в обезличенном виде, ответ и внешний ID.
8. Повторно прочитать внешний объект, если API допускает read-after-write.
9. Завершить операцию либо запланировать retry.

Ошибки `429`, timeout и `5xx` обычно повторяемые. Ошибка бизнес-валидации, неверный GTIN или окончательный отказ документа требуют внимания сотрудника.

## 12. Интеграция с МоемСкладом

- Использовать JSON API 1.2 и Bearer token отдельного пользователя с минимальными правами.
- МойСклад является master для товаров, вариантов, складов, цен и количества.
- Синхронизация использует webhooks плюс периодическую полную сверку.
- Заказ покупателя создаётся один раз и находится через `externalCode`/локальную таблицу связей.
- Отгрузка и возврат также создаются идемпотентно.
- Дополнительные поля: Avito Order ID, статус маркировки, статус ЧЗ, URL Mini App.
- На интеграционном spike проверить, разрешает ли JSON API записывать CIS в позиции нужных документов. При отсутствии возможности МойСклад хранит количество и статус, PostgreSQL — экземпляры.
- Веб-интерфейс МоегоСклада остаётся ручным fallback.

## 13. Интеграция с Авито

- Использовать только официальные методы, доступные аккаунту и выданным scopes.
- На старте выполнить capability probe и сохранить обезличенные fixtures.
- При обработке заказа учитывать `availableActions`, состав позиций и актуальное состояние.
- Передавать код только после локальной проверки позиции и GTIN.
- Не ставить локальный статус `MARKED_IN_AVITO` по одному HTTP 2xx без проверки содержимого ответа/повторного чтения.
- Учитывать лимиты, `429`, пагинацию и изменение заказа между чтением и записью.
- Не автоматизировать UI Авито браузерными кликами, если операция доступна через API.

## 14. Интеграция с Честным знаком

- Не хардкодить формат документа по памяти; сверять с актуальной документацией и тестовым контуром.
- Для прямого режима подписывать именно требуемые байты документа отсоединённой УКЭП.
- Закрытый ключ и PIN не покидают локальный компьютер.
- `local-signer` устанавливает только исходящее защищённое соединение и получает ограниченные задания на подпись.
- Для ИП не заполнять КПП там, где его не должно быть.
- Хранить идентификатор документа, статус обработки и ошибки по каждому коду.
- Успех означает финально принятый документ и подтверждённое состояние кода, а не только успешный `POST`.

## 15. Безопасность

- Проверять подпись Telegram `initData` на backend и срок `auth_date`.
- Доступ только разрешённым `telegram_id`.
- Роли: `ADMIN`, `WAREHOUSE`, `ACCOUNTANT`, `VIEWER`.
- Секреты не коммитить и не передавать во frontend.
- CIS, токены, сертификаты, PIN и персональные данные маскировать в логах.
- Все ручные переходы и повторные операции писать в audit log.
- Опасные операции требуют явного подтверждения и причины.
- Webhook endpoints должны иметь секрет, дедупликацию и защиту от replay.

```text

ЧЗ: в обороте / выбытие / выбыл / возврат / ошибка
```

## 17. Этапы реализации

### Этап 0. Integration spike

Результат — `docs/integration-capabilities.md` и набор fixtures.

- проверить scopes и реальные ответы Avito API;
- определить способ получения новых заказов;
- выполнить контрольную передачу DataMatrix в тестовом или безопасном заказе;
- получить пример электронного чека Авито;
- проверить состояние того же CIS в ЧЗ после расчёта;
- выбрать `CHZ_SUBMISSION_MODE`;
- проверить JSON API МоегоСклада для заказа, резерва, отгрузки, возврата и кодов маркировки;
- зафиксировать rate limits и retry semantics.

Без завершения этапа нельзя окончательно реализовывать отправку документов ЧЗ.

### Этап 1. Каркас

- создать pnpm monorepo;
- поднять PostgreSQL и Redis в Docker Compose;
- настроить Drizzle ORM, Drizzle Kit, первую схему и миграции;
- реализовать Fastify, health checks и конфигурацию Zod;
- подключить Telegraf webhook;
- создать Mini App и проверку Telegram initData;

## 18. Definition of Done

Система считается готовой к рабочей эксплуатации, когда:

1. Заказ Авито автоматически появляется в Mini App и МоемСкладе.
2. Остаток резервируется без дублей.
3. Сканер корректно читает коды с ASCII GS.
4. Нельзя привязать один CIS к двум активным заказам.
5. Неверный GTIN блокируется до отправки.
6. Авито подтверждает переданные коды.
7. В МоемСкладе создаётся ровно одна отгрузка.
8. Код выводится ровно одним настроенным каналом.
9. Состояние ЧЗ подтверждается после операции.
10. Отмена корректно освобождает товар.
11. Невыкупленная посылка не возвращается на склад до физической приёмки.
12. Исправный возврат снова становится доступным только после возврата кода в оборот.
13. Брак не попадает в продаваемый остаток.
14. Повтор job после сбоя не создаёт дубликаты.
15. Потеря Redis не приводит к потере бизнес-операции.
16. Полный CIS, токены и PIN отсутствуют в логах.
17. Критические сценарии покрыты интеграционными и end-to-end тестами.
18. Есть инструкция запуска, миграций, восстановления и ручного fallback.

## 19. Правила работы ИИ-агента

- Начинать с вертикального сквозного сценария, а не с полной UI-системы.
- Перед использованием внешнего endpoint сверять актуальную официальную документацию.
- Не выполнять реальные операции Авито, МоегоСклада или ЧЗ без явно настроенного окружения и подтверждения.
- Для разработки использовать адаптеры, mocks и обезличенные fixtures.
- Не делать предположений, что HTTP 2xx означает завершённую бизнес-операцию.
- Не смешивать статусы трёх внешних систем в одно поле.
- Не добавлять Kafka, RabbitMQ, микросервисы, Kubernetes или event sourcing без подтверждённой необходимости.
- Использовать Drizzle как единственный ORM; raw SQL применять только для возможностей PostgreSQL, которые неудобно или невозможно выразить через ORM.
- Не выделять Telegram-бот в отдельный репозиторий или сервис без независимой причины развёртывания.
- После каждого этапа запускать typecheck, тесты и миграции с чистой БД.
- Каждое спорное архитектурное решение фиксировать коротким ADR.
- При блокировке внешним доступом продолжать с mock adapter, явно помечая непроверенное предположение.
